# ADR 0008 — The shared mixes file and the queue top-up

- **Status:** Accepted (2026-11-16; brief `docs/plans/mixes.md`, decisions 6, 7 and 9)
- **Context:**
  - A mix is a saved recipe (genres, artists, albums from one source) that both frontends play: the GUI creates and edits mixes, the TUI plays them. Until now every file was written by one app only (the GUI keeps its own session and history under `coda-app/`, so the two never overwrite each other's queue).
  - A mix plays endlessly, but the player is pure, has no callback and stops at the end of the queue; the queue does not know who filled it, and its `revision()` also changes on ordinary edits. `MAX_QUEUE_LEN` (10,000) caps every queue.
- **Decision:**
  - **One shared file:** `$XDG_DATA_HOME/coda/mixes.json` (else `~/.local/share/coda/mixes.json`; `config::mixes_file_path`). Mixes are user data, not state or configuration, and both apps read the same file. Versioned JSON (`{"version": 1, "mixes": [...]}`), pretty-printed.
    - **Every change re-reads:** `mix::store::{add, update, delete}` each take an exclusive `flock` on `.mixes.json.lock` beside the file, read the file again, apply that one change by mix id and write the result atomically (temp file 0600, `fsync`, rename, directory `fsync`; the shared `fsio::write_atomic`, moved out of `session`). Neither app ever writes a list it held in memory, so two apps editing at once both keep their change. `load` reads under a shared lock and sets a bad file aside only under the exclusive lock after reading it again, so a reader never sets aside a file another app has just saved. A change is written pretty-printed, or compact when only that fits the cap, so deleting from a file that loaded always works. Mix ids are random (16 hex digits), so two apps adding at once cannot collide.
    - **Untrusted input:** 8 MiB cap, each mix checked like a new one (name, source, at most 50 ingredients, ids), unusable mixes and ingredients skipped, at most 500 mixes. An unreadable file is kept as `mixes.json.bad.<secs>` and an empty list used; a change then starts from empty. A file of a **newer** version is left alone (read as empty, changes refused), so an older build of one app never overwrites what a newer build of the other wrote.
    - **Any new ingredient kind or new field bumps `VERSION`** (`mix::store::VERSION`): an older build drops what it does not know when it rewrites the file (a mix left with no ingredient it knows is dropped whole), so it must see a newer version and refuse instead. Skipping unknown ingredient kinds at the same version only covers hand edits.
    - No URLs or credentials: a Navidrome mix records `navidrome::server_id` (FNV-1a of base URL and user, moved to core from the GUI history, which keeps the same values).
  - **The mix owns the queue it filled:** `Queue::clear` (which is also how `play_context` replaces the queue) bumps a `context` counter, and nothing else does. `ActiveMix::start` replaces the queue with 25 songs and records the context; once it differs, the mix has ended (decision 7). Adding, reordering, removing and skipping keep it. The session saves the active mix (its id, or a quick mix's recipe) and a restored mix adopts the restored queue.
  - **Top-up before the end:** each frontend asks `ActiveMix::wants_top_up` after it applies events and intents; with 5 or fewer entries after the current one, 20 more are appended (`enqueue_all`) and the frontend dispatches the commands `ActiveMix::top_up`/`append` return, so the next track is announced again and gapless playback holds (ADR 0005). Appending never interrupts playback; only when playback stopped because a track that played reached the end of the queue (`Player::stopped_at_end`: the user skipped past the last entries, or a Navidrome refill came late) does it play on, with what `>` would play: the entry after the ended one in the resulting queue (a song the user queued meanwhile comes first, in queue order), else the first appended song. Not after a stop, a pause (Space, or one the backend reports; a later unpause does not re-arm it), `<`, an error, a track that ended without playing, a restore, or a removed last entry, so an unavailable backend or a queue of failing songs never resumes in a loop. Topping up early also means Repeat All never wraps and the player never stops at the end, so the repeat mode is left alone.
  - **The cap:** when an append would pass 10,000 entries, the oldest already-played entries are removed first (`Player::remove_played`); the current entry and everything after it stay.
- **Alternatives:**
  - **The config directory, beside `config.toml`:** the config writer rewrites that file whole; keeping user data out of it keeps both simpler. **The state directory:** state can be thrown away; mixes cannot.
  - **Last writer wins:** simpler, but an app that loaded the list at startup would silently undo the other app's edits.
  - **A player callback or an "end of queue" event:** the player would have to know about mixes; a pure check by the caller keeps it a coordinator.
  - **Comparing `revision()`:** it changes on every edit, so it cannot tell a replace from an add.
  - **Stopping at the cap:** an endless mix would end after about 10,000 songs.
- **Consequences:**
  - A mix the file reader cannot use is dropped from the list and lost at the next write; an older build that reads a newer *version* refuses to write instead.
  - `flock` is advisory: only Coda's own writers take it. A file edited by hand while an app writes may lose the hand edit.
  - Each frontend must call `wants_top_up` after every batch it applies; a frontend that forgets stops at the end of the queue like any other queue.
  - A reader takes the lock too (shared), so reading the file needs the data directory to be writable for the lock file; without it the file is read unlocked and never set aside.
