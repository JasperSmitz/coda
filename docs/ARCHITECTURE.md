# Coda — Architecture

> **Status:** M1–M10 implemented (1.0); since the monorepo migration (ADR 0006) the engine is the shared crate `coda-core` and the terminal player is `coda-tui`. The per-slice history is in `docs/DEVELOPMENT_LOG.md`, the migration in `docs/MIGRATION_LOG.md`. This file covers the workspace, the engine and the terminal frontend; the desktop app's is `apps/coda-gui/docs/ARCHITECTURE.md`. Update it to describe reality as work ships. Do not present proposed modules as existing code.

## Workspace

```text
crates/coda-core   lib coda_core   the engine (no UI code)
      ▲                    ▲
crates/coda-tui            apps/coda-gui/src-tauri   (+ React frontend in apps/coda-gui/src)
lib coda_tui, bin coda     coda-app, lib coda_app_lib
Ratatui + Crossterm        Tauri 2
```

- One Cargo workspace (root `Cargo.toml`, resolver 3) and one `Cargo.lock`. Shared dependency versions are in `[workspace.dependencies]`; members add their own features.
- **Dependency rule:** `coda-core` depends on no frontend and no UI toolkit; `coda-tui` and `coda-app` depend on `coda-core` and never on each other (`cargo tree -p coda-core -e normal --target all` has no ratatui, crossterm, tauri, souvlaki or webview crates).
- **In `coda-core`:** every module of the module map below except `app`, `setup`, `ui` and `main`, plus `setup_actions` (the UI-free half of setup and settings: the drop guard `Reply`, `check_folder`, `ping`, the keychain-then-config saves `save` and `save_navidrome`) and `logging` (the file log and its clamps, see `main`). Additions made for the desktop app are listed in `apps/coda-gui/docs/ARCHITECTURE.md` (e.g. `cover::load`, `Player::seek_absolute`, `Queue::move_entries`, `config::navidrome_client`, `session::read_valid`, Navidrome album/artist ids).
- **In `coda-tui`:** `app`, `setup`, `ui::*` and `main`, the only code that uses Ratatui or Crossterm.
- **Frontend-specific on purpose:**
  - TUI: drawing, keymap, terminal cover-art rendering and detection (`ui::cover`), the setup and app event loops, and mpv looked up on `PATH` only (`mpv::spawn(MpvOptions::default())`; the TUI's CLI tests rely on it).
  - GUI: the engine actor, serializable DTOs and Tauri commands, the browse/history/playlist caches, media keys (souvlaki), themes, mpv lookup with fallbacks for desktop launchers (`playback::spawn_backend`, `mpv::process::default_program`), and its own session, history and log under `$XDG_STATE_HOME/coda/coda-app/`.
  - Shared by both: the config file, the keychain entries and the cover cache.
  - Visualizer: the band measurement (`playback::mpv::visualizer`) and the smoothed bars (`visualizer::Meter`) are in core; each frontend draws them its own way.
  - Lyrics: parsing, reading, searching and the Navidrome lyrics cache (`lyrics`, `lyrics::index`, `lyrics::cache`, `navidrome::Client::lyrics`) are in core; only the GUI shows and searches them (its Now Playing lyrics mode, its Search page's Lyrics section), so the TUI could add either without engine work.
- **Features:** core's `mock-secret-store` replaces the OS keychain with an in-memory store, for pty smoke builds only (coda-tui forwards it); `test-util` only exposes `SecretStore::mock()` to other crates' tests (coda-tui's dev-dependency uses it; ADR 0006, LESSONS).
- **Profiles:** the TUI ships with the default `release` profile (unwind); the GUI with `[profile.release-gui]` (LTO, `panic = "abort"`).

## Intended boundaries

```text
Ratatui frontend / keyboard input
             |
       application commands
             |
  player state + unified queue
       /             \
local source       Navidrome source
             |
    playback controller
             |
     mpv JSON IPC backend
```

The drawing is conceptual, not a dependency diagram. Source adapters locate/browse tracks and resolve playback requests; the playback controller is responsible for controlling mpv.

## Responsibilities
- **Domain:** track/source identity, queue semantics, player state and commands; no terminal widgets.
- **Sources:** browse/scan metadata and resolve local paths or authorized remote streams. Local files, and Navidrome via Subsonic/OpenSubsonic.
- **Playback:** mpv process lifecycle, JSON IPC, playback status/progress and error reporting.
- **Application:** coordinate async tasks and propagate player state/events to the UI.
- **TUI:** draw views and translate keys to commands; never block on file/network I/O.

## Decisions / constraints
- A Cargo workspace with one shared engine crate and one crate per frontend (ADR 0006); no further splitting without a real packaging or reuse need.
- Use mpv through IPC rather than shell-interpolated commands or reimplementing audio decoding (ADR 0001).
- Coda exclusively owns the queue; mpv holds the current track and at most a copy of the next one, which it may play on by itself without a gap (ADR 0002, amended by ADR 0005). Stale events are filtered by load id; an advance to a track that is no longer next is corrected with a `replace`.
- The playback boundary is a command enum in and an event enum out over Tokio channels, with one concrete mpv backend and no trait.
- The application runs one `tokio::select!` loop over terminal input, playback events, scan events, signals and a redraw tick. Scans run on blocking threads; nothing in the loop awaits player or file I/O.
- Queue transitions and the advance/stale-event logic are pure code, testable without mpv or a terminal.
- Supported platforms: Linux and macOS. Windows is out of scope.
- Logs go to a file only; raw IPC and playback targets are never logged above `trace`, and raw `loadfile` lines (`replace` and `append`: local paths, signed stream URLs) not at all. Library content stays out of the log at every level: no track titles, artists, album or playlist names, and no file paths (loads and failures are logged by `LoadId`, scan errors by error kind).
- Avoid early commitments on daemon mode or HEART interoperability protocol. A reusable library boundary may be enough at first.

M1 module layout and behaviour details: `docs/plans/m1-local-playback.md` (the brief; this file describes what shipped).

## Implemented modules
Module paths are relative to their crate: `app`, `setup`, `ui::*` and `main` are in `crates/coda-tui/src` (`coda_tui`); everything else is in `crates/coda-core/src` (`coda_core`).

- `config` — optional TOML file (`CODA_CONFIG`, else `$XDG_CONFIG_HOME/coda/config.toml`, else `~/.config/coda/config.toml`) plus env overrides. Music directory: CLI > `CODA_MUSIC_DIR` > file (absolute, validated, canonicalized). Navidrome url/user/password (file, `CODA_NAVIDROME_*`, `password_command` argv with timeout and output cap, or `password_keychain = true`; the file may name at most one, `CODA_NAVIDROME_PASSWORD` overrides all). The keychain is read before the TUI on a blocking thread; a missing entry or refused/unavailable store is exit 1 with a remedy (`coda --setup`, or `CODA_NAVIDROME_PASSWORD`) that never names the account. File permission checks for secrets; parse errors never echo source lines (ADR 0003, 0004). `Cli` has `--setup`; `Cli::try_parse_with_source` also reports whether a music directory came from the argument or `CODA_MUSIC_DIR`. `read_for_setup` reads the file for `coda --setup`: parse and permission errors (and a missing explicit `CODA_CONFIG`) still fail, but nothing is validated beyond that and nothing is resolved (no keychain read, no `password_command`), so a partial `[navidrome]`, an invalid URL, a moved folder or several password keys are prefilled for correction. It returns the raw values (a URL that parses has its username and password cleared before prefilling, and is flagged; one that does not parse but contains `@` is not prefilled at all), whether the file has content (the writer's backup rule), which hand-written password key is present, and the keychain account Coda wrote (only with `password_keychain = true` and a parseable URL and username from the file, never the env overrides). `navidrome_env_overrides` names the `CODA_NAVIDROME_*` variables that are set. `[ui] cover_art` (default `true`, a strict table like the others) turns cover art on or off (`Config::cover_art`).
- `secret_store` — the only user of `keyring-core` 1.0 and its store crates (the `keyring` 4.x ecosystem, see below): `SecretStore::{system, get, set, delete}`, service `coda`, account `<username>@<host>[:<non-default port>]`. Backends: `apple-native-keyring-store` (login Keychain) on macOS, `zbus-secret-service-keyring-store` with `crypto-rust` on Linux (pure-Rust D-Bus and crypto: no libdbus headers or OpenSSL at build time; a running Secret Service at run time). Store errors are reduced to `SecretError::{Missing, Unavailable, Denied, Failed}` because the crates' own errors can name the account or carry secret bytes. The process-wide store is cached once opened (a failed open is retried). Unit tests and the `mock-secret-store` cargo feature (pty smoke runs only) use `keyring-core`'s in-memory mock store instead, so no test touches the real keychain; a feature build calls it "test store (in memory, not saved)" on screen and logs a warning when it opens it. Not the `keyring` crate itself: its v1 facade always installs the platform store and cannot be pointed at a mock, and its docs recommend `keyring-core` plus chosen stores for applications that need that control.
- `onboarding` — pure setup state machine (first run, or a redo for `coda --setup`): screens Welcome → Music folder (skippable) → "Navidrome?" (Esc back to the folder) → server form (URL, username, password; skippable) → Ready (summary, save) or Nothing (both skipped, exit 0 without writing). Abstract `Input`s and driver `Response`s in; `Request::{CheckFolder, Ping, Save}` out with ids, so stale or abandoned answers are ignored. The server form is a separate `ServerForm` (URL, username, masked password, focus, inline error; Enter moves on or submits a validated `Server`, Esc cancels), shared with the in-app settings, as is `navidrome_blocked_by` (the env-override rule). URLs without a scheme get `https://` and are validated with `parse_base_url`. The password is a `Password` and is shown masked (`LineInput::masked`); `Debug` of the state, requests and servers is redacted. Quit (Ctrl-C, hinted on every screen) is ignored while saving, so the process never stops between the keychain write and the config write. `Onboarding::redo(Redo, suggestion)` prefills the folder (input capped at 4,096 chars), URL and username (never the password; the form focuses the first empty field); a value the input cannot hold exactly (too long, control characters) is left out with a note, and a redo with nothing to prefill uses the first-run welcome and the `~/Music` suggestion. It and carries what is set outside Coda by name: `CODA_MUSIC_DIR` or the `MUSIC_DIR` argument, the set `CODA_NAVIDROME_*` variables, and a hand-written `password`/`password_command`. In a redo, skipping a source removes it, and skipping Navidrome without a folder (from the question, the form's Esc or `s` after a failed save) returns to the Navidrome question with "Keep at least one source" instead of the Nothing screen; Ctrl-C leaves without changes. While `CODA_NAVIDROME_URL` or `CODA_NAVIDROME_USER` is set without `CODA_NAVIDROME_PASSWORD` (`Redo::navidrome_blocked_by`), a redo never opens the server form (no ping, no keychain write: startup would look the password up under the env-merged account); it names the variables and offers `k` keep `[navidrome]` as it is (`Request::Save { keep_navidrome }`) or `n` remove. Removing Navidrome while some but not all `CODA_NAVIDROME_*` variables are set shows on Ready that they must be unset too (startup would otherwise report a partial configuration). First run cannot see these variables (any of them makes the config a "partly configured" error, not `NoSource`).
- `setup` — the setup driver, run by `main` when `Config::load` returns `NoSource` and stdin and stdout are terminals, or for `coda --setup` (`Context::redo` with a `RedoContext::from_start` built from `read_for_setup`; a folder given as argument or `CODA_MUSIC_DIR` is validated first, as on a normal start, and without a terminal on both stdin and stdout it is a usage error, exit 2), before mpv is spawned. Its own short TUI session with the same discipline as `app::run` (panic hook chained to and then restored to the previous hook, `ManuallyDrop` terminal released explicitly, restore on every exit including SIGTERM/SIGHUP/SIGINT). Folder checks and the save (keychain first, then config) run on blocking threads, the ping with a temporary `navidrome::Client` on a Tokio task; each request answers exactly once through a drop guard. If the config write fails after the password was stored, the new entry is deleted again (best effort), unless it is the previous config's own entry (unchanged account, overwritten in place). On a redo, once the config is written, the keychain entry Coda wrote for the previous config is deleted best effort when the account changed or Navidrome was removed (not when it is kept); a failure is logged by kind only and does not fail the save. A terminating signal during a save waits up to 5 s for it to answer before leaving. Logs only kinds and outcomes. The keychain-then-config sequence (`store_then_write`) is shared with the in-app settings through `save_navidrome`, which writes only `[navidrome]` and returns the file's `scrobble`; the drop guard `Reply<R>` and `ping` are shared too. These UI-free parts are `coda_core::setup_actions`; `setup` keeps the driver, its event loop and `spawn_request`. Afterwards `main` reloads the config with `Config::load` (with the same music directory argument) and continues the normal startup. Known gap: Tokio's signal handlers stay installed once setup registered them, so a SIGTERM/SIGHUP/SIGINT that arrives after setup ends but before `app::run` listens again (keychain read, mpv start) is swallowed instead of ending the process.
- `config_writer` — writes the setup's choices (`write`), or for the in-app settings only `[navidrome]` (`write_navidrome`: `music_dir` and `scrobble` are kept by value from the existing file, which must parse, else nothing is written; returns the backup and the `scrobble` setting; removing `[navidrome]` from a file without a `music_dir` is refused, `NO_SOURCE_LEFT`, so the file always keeps a source): `music_dir` as typed (`~/` kept), `[navidrome]` `url`, `username`, `password_keychain = true`, behind a comment header; hand-escaped TOML basic strings. `NavidromeSection::{Remove, Keep, Write}`: setup decides every other setting the file can hold, so only `scrobble` is kept from an existing file, plus, with `Keep`, every `[navidrome]` key by value (the existing file is re-read strictly, unknown keys rejected as by the loader; if it cannot be parsed, or no longer has `[navidrome]`, the save fails instead of losing the section). Atomic 0600 temp file + fsync + rename, missing parent created 0700 (a relative `CODA_CONFIG` without a directory means `.`); a symlinked `config.toml` is replaced by a regular file and its target left unchanged; an existing file is hard-linked to `config.toml.bak.<secs>` first unless it holds only whitespace and comments, or is byte for byte what Coda writes for its own settings (`needs_backup`: Coda's header and only keys Coda writes; another comment, a hand-written `password`/`password_command` or a changed layout still gets a backup), so repeated saves do not pile up backups. `[ui]` (`cover_art`) is kept by value by every write, like `scrobble`, and written last.
- `settings` — pure state of the in-app Settings overlay (`O`), no I/O and no Ratatui. A `Context` built by `main` says what it shows and may change: the config path, the music folder of this run and where it came from (`CODA_MUSIC_DIR` or the argument), the `CODA_NAVIDROME_*` variables that are set, and who owns Navidrome (`Navidrome::{NotConfigured, Coda { url, username, account }, Outside { by }}`; Coda-owned means `password_keychain = true` and no `CODA_NAVIDROME_*` variable; `by` names the variables or the hand-written `password`/`password_command` key, never values). Overview keys: `c` Connect (not configured), `e` Edit (Coda-owned; prefilled except the password), `d` twice within 3 s Disconnect (Coda-owned; refused unless the config file has a `music_dir`, `Context::file_has_music_dir`, which `main` reads from the file when the run's folder came from the argument or `CODA_MUSIC_DIR`; the writer enforces the same rule), Esc/`O` close. The form is `ServerForm`; a submit emits `Request::Ping`, its success `Request::Save` (with the previous Coda account), a disconnect `Request::Disconnect`; ids filter stale or abandoned answers (Esc stops waiting for a ping). Keys are ignored while saving, so the overlay never closes between the keychain and the config write. Connect and edit are refused (with the variable names) under the env-override rule, or without a config location. A successful save or disconnect returns a `Change` for the app. `Debug` redacts URLs, users, accounts and paths.
- `model` — `Track`, `count` ("1 track", "1,234 tracks"), `TrackSource::{Local, Navidrome { song_id }}`, metadata with fallbacks and length caps. `Track::cover_art` is Navidrome's `coverArt` id (opaque, like song ids; always `None` for local tracks). `album_artist` comes from lofty's `ItemKey::AlbumArtist` for local files and from OpenSubsonic's `displayAlbumArtist` for Navidrome songs (`None` when the server does not send it).
- `queue` — pure ordered queue addressed by `QueueEntryId`, capped at 10,000 entries: append/insert, move up/down, clear, shuffle-after-current with injected randomness (small SplitMix64 `Rng` seeded from `getrandom`), and a revision counter for change detection. "Play next" (`insert_next`, `Placement::Next`) inserts after the current entry, behind the last entry it inserted (`next_anchor`), so consecutive `A`s keep press order; the anchor is data on the queue, not saved, and is forgotten when `current` changes (playback advancing, `<`, playing another entry, removing the current entry) and on shuffle and clear. Appending, moving and removing other entries keep it; if the anchor entry is gone or now comes before the current one, inserts go right after the current entry again. Several tracks go in as one splice (`insert_all_next`, `Player::enqueue_all`). Without a current entry `insert_next` appends (and the status line says "Added"). `shuffle_all` is "Shuffle all"'s pick for both frontends (every track in random order; a uniform sample of `MAX_QUEUE_LEN` from more, via `sample` over indices); `shuffle_all_message` is its shared status text.
- `player` — pure coordinator: user intents and `PlaybackEvent`s in, `PlayerCommand`s out (loads carry the `TrackSource`). Credential-free. Auto-advances only on EOF/error of the current `LoadId`, or follows a gapless `Advanced { from, to }` when `from` is current. `sync_next` (called by `resolve::dispatch` after every batch, so after every queue edit too) announces the entry after the current load as `PlayerCommand::SetNext { after, next }` with a fresh `LoadId` whenever it changes: the queue's next entry, the first under repeat all, the current entry again under repeat one once proven; "nothing next" only when something was announced before. An advance to the announced load, or to an earlier announcement of the same *local* queue entry after the same load (the queue changed and changed back; the same file, so nothing is cut; remote entries are excluded because an earlier copy may have been signed by another client), moves the queue on like an EOF (an unproven `from` counts as a failure, so instant-EOF queues still terminate under every repeat mode); an advance to anything else is corrected like an EOF of `from` (a `Load` of the right entry, or `Stop` if nothing follows). Until the new load's `Started` (when it is heard), `status`, `position`, `duration`, `playing_entry` and `audible_load` describe the previous track (its tail still plays); the queue's current entry has already moved. While the previous track is still heard, `>` loads the queue's current entry (the one not heard yet) and `<` restarts or leaves the track heard (a load, since a seek would go to the new track); seeks are no-ops. `client_changed` (a client swap) announces a remote next entry again and, during a gapless change to a remote entry, loads that entry again (paused if the player was) so a stream signed by the old client is never heard. `play_context(tracks, start)` (Enter/`s` in the library) is the one operation that replaces the queue: it clears it, appends the context (only the `context_window` of 10,000 that holds `start`, dropping entries before it first, then from the end) and plays `start` as a user load (fresh `LoadId`, so the replaced load's events are stale; failures in a row reset; the repeat mode kept); it does nothing for an empty context or while playback is unavailable. `play_tracks(tracks, start, shuffle, rng)` is both frontends' play-in-context: `shuffle_with_first` for a shuffled play (the start track first), then `play_context`, returning how many tracks did not fit. `RepeatMode::{Off, All, One}`: a repeat reload or wrap is a fresh load, so stale-event filtering is unchanged. A load counts as *proven* once it reports ≥ 1 s of position after `Started`; an unproven EOF is treated like a failure (it advances instead of repeating), and failures in a row stop playback once they reach the queue length, so repeat can never hot-loop. Consequence: tracks shorter than about 1.25 s are never repeated.
- `resolve` — turns `PlayerCommand`s into backend `PlaybackCommand`s: local path → `PlaybackTarget::File`, Navidrome song → freshly signed `PlaybackTarget::Stream`. An unresolvable load is fed back to the player as `TrackEnded { Error }` so the queue advances; when Navidrome is not configured, runs of remote entries are skipped in one pass to the next local entry. A `SetNext` whose entry cannot be resolved goes out without one (its own load reports the problem when reached). `dispatch` ends with the player's `sync_next`. Shared by the app and real-mpv tests.
- `navidrome` — Subsonic client (`reqwest`/rustls): salted-token auth with a fresh salt per request, ping/getArtists/getArtist/getAlbum/search3/getPlaylists/getPlaylist/getAlbumList2, playlist writes (createPlaylist, createPlaylist with `playlistId` to replace the songs, updatePlaylist to add or rename, deletePlaylist; one request each; an empty replace is refused unsent, `Error::EmptyReplace`, because Navidrome ignores it), stream URL signing. `getPlaylists`/`getPlaylist` also give `Access` (`owner`, capped, and OpenSubsonic's `readonly`; editable only by an owner equal to the configured username, compared case-insensitively, and not flagged). **Write transport:** `Client::transport` asks `getOpenSubsonicExtensions` once per client (clones share a `tokio::sync::OnceCell`); if it lists `formPost`, writes are `application/x-www-form-urlencoded` POSTs to the bare endpoint URL with the auth parameters in the body, at most 512 KiB (`MAX_POST_BODY_BYTES`, under nginx's default 1 MB); otherwise GETs whose URL must stay within 8 KiB (`MAX_GET_URL_BYTES`). Only a definite answer is remembered: the list, a Subsonic error other than rejected credentials, or HTTP 400/404/405/410/501 (a server without the endpoint: GET). Anything else (network errors, rejected credentials, 401, 403, 408, 429, 5xx, redirects, an unreadable body) fails the write and is asked again next time. A request over its limit is refused before sending (`Error::RequestTooLarge`); `id_batches` splits id lists into requests that fit, computing the exact encoded size (salt and token have fixed lengths). Bodies and URLs are never logged. **What Navidrome does** (checked in its source, commit `ec2e0a9`, 2026-10-23): `getOpenSubsonicExtensions` is public and lists `formPost` v1; a `postFormToQueryParams` middleware on every endpoint parses the form body (10 MB `MaxBytesReader`) into the query, so auth in the body works; endpoints are registered for every method, so GET works too; `getPlaylists` returns all of the user's playlists plus other users' public ones, with `owner` (the username) and `readonly` (true for other users' playlists and smart playlists); `createPlaylist` with `playlistId` replaces the tracks in the given order, duplicates kept (owner or admin only; smart playlists refused) and returns the playlist; `updatePlaylist` deletes the 0-based `songIndexToRemove` positions before appending `songIdToAdd`; owner or admin only. **Missing files:** `getPlaylist` loads only entries whose media file is not missing (`GetWithTracks(…, includeMissing=false)`: `Where(Eq{"missing": false})`), but `songIndexToRemove` deletes by stored position (`playlist_tracks.id = index + 1`), which counts every entry; so an index from the shown list can name another entry, and Coda never removes by index. A replace (`createPlaylist` with `playlistId`) deletes every row and inserts the given ids, so **removing a song or saving a new order drops the entries Navidrome hides**: missing files, and (filtered when the playlist is loaded, by `applyLibraryFilter`) songs in libraries the user cannot access. Navidrome's `songCount` counts all of them (`refreshCounters`, run on every track change, filters neither), so `PlaylistSongs::hidden_entries` compares `songCount` with the entries returned: more stored is `Hidden::Some(n)`, fewer stored is `Hidden::Suspect` (the counts disagree, so hidden entries cannot be ruled out), no `songCount` is `Hidden::None` (no warning; the drop above still applies). With hidden entries, `D` (remove) and `w` first warn, instruction first so a narrow status line keeps it ("Press w again to save: this also removes N entries Navidrome hides (missing files or other libraries)") and act only on a second press within 3 s with nothing in between (`EditArm::Remove`, `EditArm::SaveOrder`); `J`/`K` stay allowed. The confirmed count travels with the edit (`hidden`, `Hidden::bound`, `Suspect` as unbounded), and the stale check refuses (`Stale`) when the refetched playlist hides more than that, so a replace never drops more than the user confirmed. A replace with no ids leaves the tracks unchanged (`Put` only rewrites tracks when there are some), so the last song cannot be removed this way. Admins can therefore change other users' playlists on the server, but Coda only edits the user's own. Timeouts, 8 MiB streamed body cap (24 MiB for `getPlaylist`: a realistic OpenSubsonic entry with several artists, contributors and a long path is about 2 KB, so 10,000 entries are about 20.6 MB), redirects disabled, URLs stripped from errors, lenient parsing of untrusted responses. `getAlbumList2`'s `type` comes from the closed `AlbumSort` enum and `size` is clamped to 1..=500; a page reports how many items the server sent (`AlbumPage::served`, usable or not), so skipped items still advance the offset and a short page is detected. `getPlaylist` likewise reports `PlaylistSongs::served`, so a playlist cut at the entry cap is shown as "first 10,000 of N". Each call parses its own reply type (`api::Reply`: `status`, `error` and its one section; every other key is drained), and all objects built from one response share a budget of 100,000 (`MAX_RESPONSE_OBJECTS`, a thread-local reset by a guard around each synchronous `api::parse`, also on error or panic), because lists nest four deep (`artists.index[].artist[].album[].song[]`) and per-list caps alone multiply; objects past it are drained. Parsing never builds a `serde_json::Value`, in any section: sections and list items are read straight into typed structs (`ObjectSeed` through `next_element_seed`; an item that is not an object is drained), every field goes through a visitor that accepts only the scalar it expects and drains arrays and objects with `IgnoredAny`, unknown keys are skipped unparsed, strings are copied only up to the 512 chars kept and oversized ids not at all, and lists keep a capped number of items (500 albums per page, 10,000 playlists, 10,000 playlist entries, 50,000 for any other list), draining but counting the rest. A duplicate key Coda reads fails the response. Measured peak RSS against the cost of just reading the body: nested empty objects (index → artist → album → song) fill the budget and add about 19 MB, at 8 MiB through `getArtists` and at 24 MiB alike (before the budget: 435 MB and 1.31 GB); the same 24 MiB body through `getPlaylist`, which drains `artists`, adds 0.07 MB; a 16 MB body whose one entry holds a nested array of small objects (in a known field or an unknown key) adds about 0.1 MB (about 1.5 GB with `Value`-based items); 10,000 realistic 2 KB entries (20.6 MB) add 4.3 MB. Song counts and durations of albums and playlists saturate. `Password`, `StreamUrl` and `Client` redact in `Debug`/`Display`. **Cover art:** `coverArt` is read (with the same lenient `id` field parser, under the response budget) on songs and albums in `getAlbum`, `search3`, `getRandomSongs`, `getPlaylist` and the album lists; a song of `getAlbum` without its own takes the album's (`RawAlbum::into_tracks`). `Client::cover_art(id, size)` sends `getCoverArt` (signed like every request, never logged), caps the body at 4 MiB while it streams (`MAX_COVER_BYTES`) and classifies the reply by its first bytes, never by `Content-Type` (`cover::sniff`): JPEG, PNG or WebP is `CoverBytes` (with `no_store` when `Cache-Control` says `no-store`, which is how Navidrome marks its placeholder for items without art); a Subsonic error body (Navidrome answers HTTP 200, code 70 for unknown art) is `Error::Server`/`Error::Auth`; anything else `Error::Decode`. Redirects are not followed, as everywhere.
- `playback` — boundary types and `PlaybackHandle` (unbounded commands, bounded events). The gapless lookahead crosses it as `PlaybackCommand::SetNext { after, next }` in and `PlaybackEvent::Advanced { from, to }` out (see the contract in `playback/mod.rs`). The visualizer crosses it as `PlaybackCommand::SetVisualizer(bool)` in and backend-neutral `PlaybackEvent::Visualizer { load, frame }` (a `VisualizerFrame`: L/R levels and 7 bands at 63 Hz–16 kHz, each `0.0..=1.0`, a band `None` when the track cannot contain it) and a one-time `PlaybackEvent::VisualizerUnavailable` out; nothing mpv-specific reaches the app.
  - `mpv::visualizer` — pure: the filter graph (`GRAPH`, one constant: `@vizfmt:format=channels=stereo,@viz:lavfi=[…]`, the M6 spike's recommended graph with 2048-sample chunks; band-pass per band on a mono downmix, `astats` per channel, an `aeval` time-code channel `mod(t,32)/32`, `pan` back to stereo), defensive parsing of `af-metadata/viz` (dBFS strings, length-capped; NaN, infinities and missing keys are silence; a sample without a usable time code is dropped; extra keys ignored), a play clock extrapolated from `time-pos` (held while paused, at most 1 s ahead), the time-code aligner (readings wait until the position reaches them; repeats of the last polled time code, readings from before a seek or load, and readings more than 5 s ahead or 0.25 s behind are dropped, and so are queued readings that end up more than 5 s ahead of the position; at most 128 queued; only the newest due reading is sent), and attach/poll state. Sending a seek only drops the poll already out. mpv's own `seek` event holds positions and readings back until `playback-restart`, because mpv answers `success` to a seek it does not perform (a non-seekable stream) and then sends neither event. Only the start of the most recently sent load counts, and the graph is added once its events have been delivered. The graph is added with `af add` the first time the visualizer is wanted while a track plays (not paused, no load in flight) — never at spawn or while idle, where mpv accepts a bad graph unchecked and then fails every file. An error reply makes it unavailable for the session (reported once, never retried). While hidden it stays attached and is removed (`af remove @vizfmt,@viz`, before the `loadfile` or `stop`) only at the next load or stop, because removing it mid-track skips 23–55 ms. If a track fails while the graph is attached and before it ever produced a reading (an `af add` that raced the end of a track and landed while idle), the graph is removed and reported unavailable. Bands at or above half the track's sample rate (`audio-params/samplerate`, observed) are `None`. A gapless change (`gapless_change`) keeps the graph: polls sent before it feed the previous track's aligner, against its clock extrapolated for up to 5 s (mpv's `time-pos` is the next track's by then); later polls feed a second aligner for the next track (its time code restarts at 0; a reading older than those queued replaces them, since they were the previous track's tail); at its `Started` the second aligner takes over with its own clock.
  - `mpv::protocol` — JSON IPC encode/decode.
  - `mpv::state` — pure entry-id ↔ `LoadId` mapping (the id comes from the `loadfile` reply), load serialization and collapse, event buffering, redirect and unrequested-entry handling. The lookahead: `SetNext` applies only while `after` is the latest load or advance; once that load is mapped, `playlist-clear` and `loadfile … append` go out (one set-next in flight, later ones collapse; never `playlist-remove`/`move` or `insert-next`), and the append's reply maps the next entry. At the current entry's `end-file eof`, if an appended entry could follow, it asks `idle-active` and waits: the next `start-file` of an appended entry gives `Advanced`, `idle-active = true` (or anything else) gives `TrackEnded { Eof }`. Replies cannot settle this, because mpv writes events that happened while a command ran after its reply, while mpv picks the successor without running commands between `end-file` and the next `start-file` (checked in mpv 0.41's `ipc-unix.c` and `loadfile.c`; this assumes no `on_after_end_file` hook runs there, and Coda registers none; mpv's `idle` event also ends the wait, so it cannot hang). A set-next held back during the wait is sent once it ends. After an advance, an append for the previous track that is still unanswered or sits behind the new entry (mpv moved on before the clear ran) is cleared once the replies are in, unless the player announces a next entry first. The advanced-to entry's `Started` waits for the first `time-pos` above zero after its `file-loaded` (or comes just before its `end-file`). Appended entries that can no longer play are forgotten: when an append is answered, the clear before it has run, so of the earlier unstarted appends only the newest is kept (mpv may have moved to it just before the clear); and when a later entry starts. A started entry and the current load's entry are never dropped, however often the next entry changes. Known minor cost: when the current track ends with an error while a next entry is held, mpv opens that entry, which is stale for the player; the player's `replace` load of the next track then opens it again. A `loadfile` reply without an entry id turns the lookahead off for the session (logged once) and loads fall back to `get_property playlist/0/id`. A `ReplyWatchdog` records when each request was handed to the writer; a reply overdue by 10 s means mpv is hung. Gaps of more than 1 s between the driver's checks (a blocked consumer, a slow pre-check, a suspended process) are excused, and `Instant` does not advance during system sleep. Replies are not always immediate: after `end-file eof` on the last entry, mpv blocks while it drains its audio buffer (observed up to about 2 s on real devices), and the timeout covers that. A hung idle mpv is noticed only at the next command.

- `lyrics::index` — lyrics search (`docs/plans/lyrics-search.md`). `IndexedLyrics::new(&Lyrics)` keeps a track's lines (trimmed, blank ones dropped) once, as parsed, joined by `\n` (`None` for blank lyrics, so tracks without lyrics take no space; `text()`/`from_text()` for the cache file). Matching is on the folded form (`fold`: lowercase; `’ ‘ ʼ` → `'`, `“ ”` → `"`, `– —` → `-`; whitespace runs and line breaks → one space; no diacritic folding), but the folded text is never stored: `index/find.rs` finds a folded needle in the original text with exactly the result of `fold(text).find(needle)` (candidates are only the chars that fold to the needle's first char, from a reverse fold table built once from every char (`ж Ж`; `i I İ`; `' ’ ‘ ʼ`); a 32-byte vectorized scan looks for their ASCII bytes and the last bytes of their UTF-8 forms, then confirms the whole char; the compare folds as it goes, with a fast path for text already equal to the needle byte for byte and an early reject for a char that folds to itself and differs (a BMP bitset; folding is idempotent, checked over every char); the folded offset is counted only for the matches shown; candidates and compares are budgeted per text and fall back to fold-then-find, so adversarial text stays linear; an equivalence test runs 30,000 generated cases (every whitespace kind, case-changing and length-changing chars, quotes, dashes, Cyrillic, CJK, astral chars) and hand-written ones against the reference). A snippet re-folds that entry's lines to find the ones a match spans. `LyricsIndex<K>` is a plain list of `(key, IndexedLyrics)` (`insert`, `push`/`get`/`set`/`swap_remove` by slot, `iter`); `search(query, skip, limit, order)` folds the query (under 3 chars after folding: nothing, no work), matches every entry `skip` does not reject (one result per track, at its first match), counts them all, selects and sorts the first `limit` by the caller's order (ties by insertion order) and builds a `Snippet` for each: the original line, or the lines a match spans joined by ` / `, with the match as char ranges (none when a length-changing case mapping is split by the match). Measured on 50,000 entries × ~1.5 KB (release, x86-64 Linux): 76–77 MB held (the text once), 0.17–0.25 s to build; a search 7–58 ms in Latin script, 19–100 ms in Cyrillic (the worst for a query starting with a letter as common as `н`), 13–33 ms in CJK. `Library` owns a `LyricsIndex<TrackId>` (`add_lyrics` by path; `search_lyrics(query, exclude, limit)` in browse order, leaving out `exclude` and every track `library::search` matches for the same query, by its own predicate, so a Lyrics list beside a local search never repeats a track, even one the scan added after that search); it is rebuilt with each scan and never persisted.
- `lyrics::cache` — the Navidrome lyrics cache (slice 2; ADR 0007). One file per server and user, `$XDG_CACHE_HOME/coda/lyrics/<md5(URL, user)>.json` (`cache_dir`, `server_key`): compact JSON (version 1; when the last full refresh started and one in progress; per album id, song count, when listed; per song id, album id, title, artist, album, album artist, artist id, cover id, disc, track, duration, when checked, failed syncs in a row, lyrics text without timestamps; albums whose request failed recently, with their count), written atomically, 0600 in a 0700 folder, and only when something changed. A corrupt, unreadable, wrong-version or over-512 MB file loads as empty (debug log); it is parsed while read, one song at a time (`DeserializeSeed`), so loading peaks barely above the loaded size; temp files a crash left are deleted when a cache opens (after 10 minutes); loading cleans and caps everything like server data (`Track::navidrome`, `IndexedLyrics::from_text`, id bounds). `Store` (share in an `Arc`) holds the cache behind a `RwLock`, never held across a request: songs compactly (ids as `Arc<str>` shared by the song table, album lists and the `LyricsIndex<Arc<str>>`; each song knows its index slot, so changing or removing its lyrics is O(1); a `Track` built only for results), `search(query, &HashSet<song id>, limit) -> LyricsResults<Track>` (artist, album, disc, track order), a `watch` of `Status { state: Idle | Albums{done,todo} | Songs{done,todo} | UpToDate | Paused(Unreachable|Rejected|Failed), songs, checked, with_lyrics }`, `save`/`save_now`/`is_dirty`, `delete_file` (later saves write nothing). `sync(&store, &client, SyncOptions)`: pages `getAlbumList2` alphabetically (500 a page, at most 200,000 albums); refuses an empty list, or one under half of 20+ known albums, unless `rebuild` (`Failed`, nothing removed); drops albums no longer listed, `getAlbum` for new albums or a changed song count, then `Client::lyrics` for songs never checked; every 30 days or with `rebuild` everything again (resumable). At most 3 requests in flight (its own `JoinSet`, apart from browsing's limit). Saved every 250 items, at most every 15 s, and at the end. Errors: `Auth` and HTTP 401/403 stop the sync (`Rejected`), a redirect stops it (`Failed`); any other failed request (timeouts, 5xx, HTML pages, undecodable answers, a failed extension check) leaves the item for next time, and once the sync completes counts one failure for it: after 3 completed syncs in a row it is skipped until the next full refresh. 10 failures in a row stop the sync (`Unreachable` if all were connection problems, else `Failed`) and count nothing. A completed sync ends `UpToDate` unless at least one request in 20 failed (`Paused(Unreachable)`); a refresh completes when nothing is left. Measured (release, counting allocator, `tests/lyrics_cache_memory.rs`, Latin, Cyrillic and CJK corpora): 20,000 songs with ~1.5 KB of lyrics each (30.5 MB) hold 41.6–41.9 MB (peak while loading 41.8–42.1 MB), load in 0.17–0.21 s, search in 5–26 ms (Latin, CJK) and 7–45 ms (Cyrillic); a save takes 60–85 ms; the file is 37 MB. Wiremock tests in `tests/navidrome_lyrics_cache.rs`.
- `visualizer` — pure display state (`Meter`): the smoothed bars of one load. A louder reading moves a bar 70 % of the way at once; a quieter one lets it fall at most 1.6 of full height per second (the step capped at 250 ms, so a stall does not drop it at once). Another load starts from zero, except at the end of a gapless change, where `hand_over` relabels the bars for the new load. `spread_bands` (pure) turns the 7 band readings into N bars evenly spaced on a log-frequency axis from 63 Hz to 16 kHz, through `band_curve`: a monotone cubic (Fritsch–Butland slopes, clamped to the two surrounding bands) that passes through every available band and never overshoots; bars past the last available band (or next to any `None` band) are `None`, so nothing is invented above Nyquist.

- `navidrome::edit` — playlist edits as small sequential jobs: `EditOp::{Create, Add, Rename, Delete, Remove, Replace}` carried in an `EditRequest` (generation and id), `run` performs its requests in order, `spawn_edit` runs it on a Tokio task and answers exactly once through a drop guard (`Error::Aborted` if cancelled or panicked). `Create` sends the first batch with `createPlaylist` and the rest with `updatePlaylist` adds; `Add` batches likewise. `Remove` is a `Replace` of the shown list without that entry (see the missing-file note above; an index past the list is `Stale`, an empty result `EmptyReplace`). A replace (and so a removal) is never split (a partial replace would lose songs): if it does not fit one request it is refused before the refetch. A failure after some requests succeeded is `Partial { created, added, error }`. There is no server-side precondition, so a change between the refetch and the write (milliseconds) is not detected.
- `navidrome::browse` — pure remote browse state (`Browser`), owned by one client `Generation` that its `FetchRequest`s and `FetchResponse`s carry; a response from another generation is ignored (request ids restart with each browser): navigation stack of views rooted at a static Home (Shuffle all, Playlists, Artists, Albums; fetches nothing until an entry is used), then Artists → Artist → Album, Playlists → Playlist (songs in playlist order, duplicates kept), Albums (one view per `AlbumSort`, `o` cycles), plus Search; session cache keyed by `Resource`, at most one in-flight request per resource, FIFO enqueue jobs (song, album, playlist, artist; each with a `Placement`) completed strictly in press order, single-line search input. **Play in context:** `open_selected` (`l`) opens; `activate` (Enter) returns `JobOutcome::Play` at once for a song (the songs the view shows, in shown order, the selected one as `start`: an album, a playlist or its unsaved draft, the songs section of search results) and for a cached album or playlist, opens an artist or Home entry, and otherwise makes a play request; `play_shuffled` (`s`) does the same shuffled, artists included. The loop aborts the old client's fetches (they answer `Aborted`, which the generation check drops) and gives the new client its own fetch permits (`Fetches::restart`), starts a new ping tagged with the generation (`App::handle_ping` ignores an old one) and, with `scrobble` from the file, a new `Scrobbler`, dropping the old receivers and scrobbler. Playback is not touched: the current stream plays on, and queued remote tracks resolve with whatever client is current at their next load (without one they fail and are skipped by the existing `resolve::dispatch` path). `2` without Navidrome shows the Navidrome source with "Press Enter to connect"; Enter opens the Connect form, and the other library keys do nothing there.
- `app` maps the playlist keys: `S` in the queue saves its Navidrome songs as a new playlist (local tracks left out and counted; without Navidrome or without remote songs a message); `P` in the library opens the picker (on the local source a message: only Navidrome songs can be added); in the Playlists list `N` new, `e` rename, `D` delete; in a playlist `D` remove (one press), `J`/`K` move, `w` save, `Esc` discard. `D` on a playlist opens a y/n question (`PromptKind::Delete` in the browser's prompt slot, `Browser::confirmation`): only `y` deletes, any other key (Ctrl-C also quits) cancels, says "Not deleted" and sends nothing. Only changes that drop hidden entries need a second press, armed like `C` (`EditArm::{Remove, SaveOrder}`: the playlist, index and song id, or the playlist; 3 s; any other key disarms). While the picker is open it takes the keys (j/k, Enter, Esc/h, q); the name prompt takes them like the search input, pastes included. The loop's `EditRunner` holds the running edit (generation, id, task) and starts the next one, of any generation, only after that one has answered, so edits stay one at a time across account swaps too; edits are not aborted when the client changes (the old server's change completes; its result is dropped by the generation check). While an edit is queued or running (the browser's pending edits, or the runner's `App::edit_in_flight` flag, which `pump` sets and `answered` clears, so an edit still running for the old account after a swap counts too), the first `q`/Ctrl-C only warns ("A playlist change is being saved; press again to quit"); at exit the running edit is awaited for up to 5 s (`EDIT_SAVE_WAIT`, alongside the settings save), and queued edits that never started are dropped, logged as a count. `/` is refused over an unsaved order, like `h` and `r`.
- `app` also starts a background Navidrome `ping` after the TUI is up and reports the result in the status line; without a music directory there is no scan and the library shows "No local music directory configured".
- `main` — config (first-run setup on an interactive `NoSource`, or `--setup`; `password_command` or keychain), the settings `Context` (ownership from the loaded config and the set variables), file logging (`coda_core::logging`), optional Navidrome client (`config::navidrome_client`), mpv spawn and connect, then `app::run` on an explicitly built runtime that is shut down with a 500 ms bound (also after a panic), so a stuck DNS lookup cannot delay exit. The log filter always clamps HTTP crates (`hyper_util`, `hyper`, `h2`, `reqwest`, `rustls`) and `zbus` to warn, whatever `CODA_LOG` says, because hyper-util logs peer addresses at debug and zbus's Secret Service messages carry the keychain account. There is deliberately no `log` → `tracing` bridge: the keyring crates log the account through `log`.

Only `app`, `setup` and `ui` (all in `coda-tui`) depend on Ratatui/Crossterm. Only `secret_store` depends on the keyring crates. Only `cover` decodes images (`image`).
