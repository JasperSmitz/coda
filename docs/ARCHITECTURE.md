# Coda — Architecture

> **Status:** M1 (local playback) is implemented: core, mpv backend, library scan and TUI. M2 (Navidrome) is implemented: config file, Subsonic client, remote tracks in the unified queue, remote browsing and search. M3 (quality and convenience) is implemented: queue controls, repeat modes, session persistence, local search, Navidrome scrobbling and playback robustness. M4 slice 1 (first-run setup with the password in the OS keychain) is implemented. Update this file to describe reality as work ships. Do not present proposed modules as existing code.

## Intended boundaries

```text
Ratatui frontend / keyboard input
             |
       application commands
             |
  player state + unified queue
       /             \
local source       Navidrome source (M2)
             |
    playback controller
             |
     mpv JSON IPC backend
```

The drawing is conceptual, not a dependency diagram. Source adapters locate/browse tracks and resolve playback requests; the playback controller is responsible for controlling mpv.

## Responsibilities
- **Domain:** track/source identity, queue semantics, player state and commands; no terminal widgets.
- **Sources:** browse/scan metadata and resolve local paths or authorized remote streams. Local in M1; Navidrome via Subsonic/OpenSubsonic in M2.
- **Playback:** mpv process lifecycle, JSON IPC, playback status/progress and error reporting.
- **Application:** coordinate async tasks and propagate player state/events to the UI.
- **TUI:** draw views and translate keys to commands; never block on file/network I/O.

## Decisions / constraints
- Begin with one Rust Cargo package. Split into crates only if there is a real packaging or reuse requirement.
- Use mpv through IPC rather than shell-interpolated commands or reimplementing audio decoding (ADR 0001).
- Coda exclusively owns the queue; mpv plays one track at a time. Stale track-end events are filtered by load id (ADR 0002).
- The playback boundary is a command enum in and an event enum out over Tokio channels, with one concrete mpv backend and no trait.
- The application runs one `tokio::select!` loop over terminal input, playback events, scan events, signals and a redraw tick. Scans run on blocking threads; nothing in the loop awaits player or file I/O.
- Queue transitions and the advance/stale-event logic are pure code, testable without mpv or a terminal.
- Supported platforms: Linux and macOS. Windows is out of scope.
- Logs go to a file only; raw IPC and playback targets are never logged above `trace`.
- Avoid early commitments on daemon mode or HEART interoperability protocol. A reusable library boundary may be enough at first.

Proposed M1 module layout and behaviour details: `docs/plans/m1-local-playback.md`. They become architecture here only once they ship.

## Implemented modules
Single package `coda-player`: library `coda_player`, binary `coda`.

- `config` — optional TOML file (`CODA_CONFIG`, else `$XDG_CONFIG_HOME/coda/config.toml`, else `~/.config/coda/config.toml`) plus env overrides. Music directory: CLI > `CODA_MUSIC_DIR` > file (absolute, validated, canonicalized). Navidrome url/user/password (file, `CODA_NAVIDROME_*`, `password_command` argv with timeout and output cap, or `password_keychain = true`; the file may name at most one, `CODA_NAVIDROME_PASSWORD` overrides all). The keychain is read before the TUI on a blocking thread; a missing entry or refused/unavailable store is exit 1 with a remedy that names the file but never the account. File permission checks for secrets; parse errors never echo source lines (ADR 0003, 0004).
- `secret_store` — the only user of `keyring-core` 1.0 and its store crates (the `keyring` 4.x ecosystem, see below): `SecretStore::{system, get, set, delete}`, service `coda`, account `<username>@<host>[:<non-default port>]`. Backends: `apple-native-keyring-store` (login Keychain) on macOS, `zbus-secret-service-keyring-store` with `crypto-rust` on Linux (pure-Rust D-Bus and crypto: no libdbus headers or OpenSSL at build time; a running Secret Service at run time). Store errors are reduced to `SecretError::{Missing, Unavailable, Denied, Failed}` because the crates' own errors can name the account or carry secret bytes. The process-wide store is cached once opened (a failed open is retried). Unit tests and the `mock-secret-store` cargo feature (pty smoke runs only) use `keyring-core`'s in-memory mock store instead, so no test touches the real keychain; a feature build calls it "test store (in memory, not saved)" on screen and logs a warning when it opens it. Not the `keyring` crate itself: its v1 facade always installs the platform store and cannot be pointed at a mock, and its docs recommend `keyring-core` plus chosen stores for applications that need that control.
- `onboarding` — pure first-run setup state machine: screens Welcome → Music folder (skippable) → "Navidrome?" (Esc back to the folder) → server form (URL, username, password; skippable) → Ready (summary, save) or Nothing (both skipped, exit 0 without writing). Abstract `Input`s and driver `Response`s in; `Request::{CheckFolder, Ping, Save}` out with ids, so stale or abandoned answers are ignored. URLs without a scheme get `https://` and are validated with `parse_base_url`. The password is a `Password` and is shown masked (`LineInput::masked`); `Debug` of the state, requests and servers is redacted. Quit (Ctrl-C, hinted on every screen) is ignored while saving, so the process never stops between the keychain write and the config write.
- `setup` — the setup driver, run by `main` only when `Config::load` returns `NoSource` and stdin and stdout are terminals, before mpv is spawned. Its own short TUI session with the same discipline as `app::run` (panic hook chained to and then restored to the previous hook, `ManuallyDrop` terminal released explicitly, restore on every exit including SIGTERM/SIGHUP/SIGINT). Folder checks and the save (keychain first, then config) run on blocking threads, the ping with a temporary `navidrome::Client` on a Tokio task; each request answers exactly once through a drop guard. If the config write fails after the password was stored, the entry is deleted again (best effort). A terminating signal during a save waits up to 5 s for it to answer before leaving. Logs only kinds and outcomes. Afterwards `main` reloads the config with `Config::load` and continues the normal startup. Known gap: Tokio's signal handlers stay installed once setup registered them, so a SIGTERM/SIGHUP/SIGINT that arrives after setup ends but before `app::run` listens again (keychain read, mpv start) is swallowed instead of ending the process.
- `config_writer` — writes the setup's choices: `music_dir` as typed (`~/` kept), `[navidrome]` `url`, `username`, `password_keychain = true`, behind a comment header; hand-escaped TOML basic strings. Atomic 0600 temp file + fsync + rename, missing parent created 0700 (a relative `CODA_CONFIG` without a directory means `.`); a symlinked `config.toml` is replaced by a regular file and its target left unchanged; an existing (source-less) file keeps its `scrobble` setting and is hard-linked to `config.toml.bak.<secs>` first unless it holds only whitespace and comments.
- `model` — `Track`, `TrackSource::{Local, Navidrome { song_id }}`, metadata with fallbacks and length caps.
- `queue` — pure ordered queue addressed by `QueueEntryId`, capped at 10,000 entries: append/insert, move up/down, clear, shuffle-after-current with injected randomness (small SplitMix64 `Rng` seeded from `getrandom`), and a revision counter for change detection.
- `player` — pure coordinator: user intents and `PlaybackEvent`s in, `PlayerCommand`s out (loads carry the `TrackSource`). Credential-free. Auto-advances only on EOF/error of the current `LoadId`. `RepeatMode::{Off, All, One}`: a repeat reload or wrap is a fresh load, so stale-event filtering is unchanged. A load counts as *proven* once it reports ≥ 1 s of position after `Started`; an unproven EOF is treated like a failure (it advances instead of repeating), and failures in a row stop playback once they reach the queue length, so repeat can never hot-loop. Consequence: tracks shorter than about 1.25 s are never repeated.
- `resolve` — turns `PlayerCommand`s into backend `PlaybackCommand`s: local path → `PlaybackTarget::File`, Navidrome song → freshly signed `PlaybackTarget::Stream`. An unresolvable load is fed back to the player as `TrackEnded { Error }` so the queue advances; when Navidrome is not configured, runs of remote entries are skipped in one pass to the next local entry. Shared by the app and real-mpv tests.
- `navidrome` — Subsonic client (`reqwest`/rustls): salted-token auth with a fresh salt per request, ping/getArtists/getArtist/getAlbum/search3, stream URL signing. Timeouts, 8 MiB streamed body cap, redirects disabled, URLs stripped from errors, lenient parsing of untrusted responses. `Password`, `StreamUrl` and `Client` redact in `Debug`/`Display`.
- `playback` — boundary types and `PlaybackHandle` (unbounded commands, bounded events).
  - `mpv::protocol` — JSON IPC encode/decode.
  - `mpv::state` — pure entry-id ↔ `LoadId` mapping, load serialization and collapse, event buffering, redirect and unrequested-entry handling. A `ReplyWatchdog` records when each request was handed to the writer; a reply overdue by 10 s means mpv is hung. Gaps of more than 1 s between the driver's checks (a blocked consumer, a slow pre-check, a suspended process) are excused, and `Instant` does not advance during system sleep. Replies are not always immediate: after `end-file eof` on the last entry, mpv blocks while it drains its audio buffer (observed up to about 2 s on real devices), and the timeout covers that. A hung idle mpv is noticed only at the next command.
  - `mpv::process` — argv (incl. `--network-timeout`), private socket directory, spawn with `CODA_NAVIDROME_*` removed from the environment, connect retry.
  - `mpv` (driver) — async task: reader loop plus a separate writer task, file pre-check (files only; streams skip it and are never trace-logged), shutdown with `ShutdownOutcome`. When the watchdog trips it takes the crashed-backend path (`BackendExited("mpv stopped responding")`, bounded kill and reap, socket dir removed); there is no automatic restart. A rejected `set_property volume` becomes `PlaybackEvent::VolumeRejected { volume, reason }`, so the player drops that request and keeps the user's saved preference. `MpvOptions` (program path, `--ao=null`, reply timeout, extra args) is internal and only used by tests; `spawn_backend` always uses the defaults.
- `session` — `state.json` in the state dir: versioned JSON of queue (source + metadata, never URLs or credentials), current index, volume and repeat. Loaded before the TUI with a 16 MiB cap, `O_NONBLOCK` open + fstat, typed deserialization with a capped sequence visitor; invalid files are quarantined as `state.json.bad.<secs>` (never overwriting) and the user is told once. Saved atomically (temp file 0600, fsync, rename, dir fsync) by the app's `Saver`: debounced 2 s after a revision change, one write at a time on `spawn_blocking`, and a bounded final save at exit, run alongside backend shutdown. Restore never auto-plays.
- `line_input` — the shared single-line input (256-char cap, control-character filtering, newline/tab → space, paste) used by local and Navidrome search and the setup form, with a masked display mode for the password.
- `library::search` — synchronous case-insensitive substring search over title, artist, album and the path relative to the music root, run on submit; shows the first 1,000 matches plus the total; results are a snapshot shown as an overlay, so the browse position is kept. Accepted deviation from the M3 brief: about 14 ms worst case for 50k tracks in release (Apple silicon), roughly one frame, once per submit. Move it to `spawn_blocking` if libraries or hardware make it noticeable. No Unicode normalization, so an NFD path does not match an NFC query.
- `navidrome::scrobble` — the pure `Listen` rule, one per load of a remote track: "now playing" on `Started`; one submission at 50 % of the duration or 4 min, whichever comes first, counting only position steps of (0, 2 s] while not paused, skipping tracks under 30 s or of unknown duration; `time` is the wall-clock time captured at `Started`. The `Scrobbler` is a single worker task with a bounded queue (16; overflow is dropped and logged), separate from the browse fetch semaphore, so requests stay in order and never take browse capacity. Failures are logged by `detail()`; only the first is shown. Config `[navidrome] scrobble` (default true).
- `library::scan` / `library::tree` — blocking-thread scan with incremental batches; directory browse tree.
- `app` — App state and the single `tokio::select!` loop (terminal input, playback events, scan events, SIGTERM/SIGHUP/SIGINT, 250 ms tick); terminal lifecycle and the panic hook. Every exit runs a bounded backend shutdown, then restores the terminal.
- `ui::onboarding` — setup screens (one centred panel; typed text sanitized and tail-truncated, password masked, spinner while busy) and the key → `onboarding::Input` mapping.
- `ui::keymap` / `ui::render` / `ui::help` — key-to-action mapping per focused panel; Library, Queue, now-playing bar and status line; help overlay. Untrusted text is sanitized (control and bidi characters) and truncated by display width with bounded work. Library and Queue panels keep a persistent scroll offset and build only the visible rows, so frame cost does not grow with list length.
- `navidrome::browse` — pure remote browse state (`Browser`): navigation stack of views (Artists → Artist → Album, plus Search), session cache keyed by `Resource`, at most one in-flight request per resource, FIFO enqueue jobs completed strictly in press order, single-line search input. Emits `FetchRequest`s as data; `spawn_fetch` runs them on Tokio tasks under a 4-permit semaphore, with background enqueue jobs limited to 2 in flight so browsing is never starved. A drop guard guarantees every fetch answers exactly once (`Error::Aborted` on panic/cancel).
- `app` has two library sources (`Source::{Local, Navidrome}`, keys `1`/`2`) and a `Connection` state. It drains fetch requests at the top of each loop iteration and applies `FetchResponse`s from a channel branch. Bracketed paste is enabled; pastes go only into the search input, filtered like typed text.
- `app` also starts a background Navidrome `ping` after the TUI is up and reports the result in the status line; without a music directory there is no scan and the library shows "No local music directory configured".
- `main` — config (first-run setup on an interactive `NoSource`; `password_command` or keychain), file logging, optional Navidrome client, mpv spawn and connect, then `app::run` on an explicitly built runtime that is shut down with a 500 ms bound (also after a panic), so a stuck DNS lookup cannot delay exit. The log filter always clamps HTTP crates (`hyper_util`, `hyper`, `h2`, `reqwest`, `rustls`) and `zbus` to warn, whatever `CODA_LOG` says, because hyper-util logs peer addresses at debug and zbus's Secret Service messages carry the keychain account. There is deliberately no `log` → `tracing` bridge: the keyring crates log the account through `log`.

Only `app`, `setup` and `ui` depend on Ratatui/Crossterm. Only `secret_store` depends on the keyring crates.

## Verification
- Standard: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo clippy --all-targets -- -D warnings` (without features, so the shipping credential-store backend is linted rather than the mock), `cargo test --all-targets`, `cargo build`.
- With mpv installed: `cargo test --all-targets -- --ignored` (real-mpv lifecycle, playback, hostile-input, HTTP streaming and watchdog tests). Tests that depend on timing run mpv with `--ao=null`, because a real audio output can report EOF up to its buffer length early (several seconds for 8 kHz mono WAVs on macOS when CoreAudio falls back to avfoundation).
- Navidrome client tests run against `wiremock` and a raw TCP server (`tests/navidrome_client.rs`); no test contacts a real server.
- Event-ordering safety lives in `tests/event_ordering.rs`, which drives the real `MpvState` and `Player` through exhaustive message interleavings.
- UI rendering is covered by Ratatui `TestBackend` tests; the panic hook has its own test binary (`tests/panic_hook.rs`).
- Keychain code is tested only against `keyring-core`'s mock store (unit tests use it automatically). Pty smoke runs of the setup use a binary built with `--features mock-secret-store`, temporary `HOME`/`XDG_*` directories and a fake Subsonic server; a run against the real login keychain is a manual step for the owner.
- Verified on macOS with mpv 0.41, including pty-driven smoke runs of every exit path. Slice 1 also passed in Debian (mpv 0.35) and Arch (mpv 0.41) containers; the TUI has not been run on Linux.
