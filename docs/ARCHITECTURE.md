# Coda — Architecture

> **Status:** M1 (local playback) is implemented: core, mpv backend, library scan and TUI. M2 (Navidrome) is implemented: config file, Subsonic client, remote tracks in the unified queue, remote browsing and search. M3 (quality and convenience) is implemented: queue controls, repeat modes, session persistence, local search, Navidrome scrobbling and playback robustness. M4 slice 1 (first-run setup with the password in the OS keychain) and slice 2 (part A `coda --setup`, part B settings inside the app) are implemented. M5 slice 1 (Navidrome Home, playlists, paged album lists, `A` play next) slice 2 (local Home, tag-based artists and albums, `.m3u` playlists) and slice 3 (Navidrome playlist editing) are implemented. M6 slice 2 (the audio visualizer) is implemented. Update this file to describe reality as work ships. Do not present proposed modules as existing code.

## Intended boundaries

```text
Ratatui frontend / keyboard input
             |
       application commands
             |
  player state + unified queue
       /             \
local source       Navidrome source (M2)
             |
    playback controller
             |
     mpv JSON IPC backend
```

The drawing is conceptual, not a dependency diagram. Source adapters locate/browse tracks and resolve playback requests; the playback controller is responsible for controlling mpv.

## Responsibilities
- **Domain:** track/source identity, queue semantics, player state and commands; no terminal widgets.
- **Sources:** browse/scan metadata and resolve local paths or authorized remote streams. Local in M1; Navidrome via Subsonic/OpenSubsonic in M2.
- **Playback:** mpv process lifecycle, JSON IPC, playback status/progress and error reporting.
- **Application:** coordinate async tasks and propagate player state/events to the UI.
- **TUI:** draw views and translate keys to commands; never block on file/network I/O.

## Decisions / constraints
- Begin with one Rust Cargo package. Split into crates only if there is a real packaging or reuse requirement.
- Use mpv through IPC rather than shell-interpolated commands or reimplementing audio decoding (ADR 0001).
- Coda exclusively owns the queue; mpv plays one track at a time. Stale track-end events are filtered by load id (ADR 0002).
- The playback boundary is a command enum in and an event enum out over Tokio channels, with one concrete mpv backend and no trait.
- The application runs one `tokio::select!` loop over terminal input, playback events, scan events, signals and a redraw tick. Scans run on blocking threads; nothing in the loop awaits player or file I/O.
- Queue transitions and the advance/stale-event logic are pure code, testable without mpv or a terminal.
- Supported platforms: Linux and macOS. Windows is out of scope.
- Logs go to a file only; raw IPC and playback targets are never logged above `trace`, and raw `loadfile` lines (local paths, signed stream URLs) not at all. Library content stays out of the log at every level: no track titles, artists, album or playlist names, and no file paths (loads and failures are logged by `LoadId`, scan errors by error kind).
- Avoid early commitments on daemon mode or HEART interoperability protocol. A reusable library boundary may be enough at first.

Proposed M1 module layout and behaviour details: `docs/plans/m1-local-playback.md`. They become architecture here only once they ship.

## Implemented modules
Single package `coda-player`: library `coda_player`, binary `coda`.

- `config` — optional TOML file (`CODA_CONFIG`, else `$XDG_CONFIG_HOME/coda/config.toml`, else `~/.config/coda/config.toml`) plus env overrides. Music directory: CLI > `CODA_MUSIC_DIR` > file (absolute, validated, canonicalized). Navidrome url/user/password (file, `CODA_NAVIDROME_*`, `password_command` argv with timeout and output cap, or `password_keychain = true`; the file may name at most one, `CODA_NAVIDROME_PASSWORD` overrides all). The keychain is read before the TUI on a blocking thread; a missing entry or refused/unavailable store is exit 1 with a remedy (`coda --setup`, or `CODA_NAVIDROME_PASSWORD`) that never names the account. File permission checks for secrets; parse errors never echo source lines (ADR 0003, 0004). `Cli` has `--setup`; `Cli::try_parse_with_source` also reports whether a music directory came from the argument or `CODA_MUSIC_DIR`. `read_for_setup` reads the file for `coda --setup`: parse and permission errors (and a missing explicit `CODA_CONFIG`) still fail, but nothing is validated beyond that and nothing is resolved (no keychain read, no `password_command`), so a partial `[navidrome]`, an invalid URL, a moved folder or several password keys are prefilled for correction. It returns the raw values (a URL that parses has its username and password cleared before prefilling, and is flagged; one that does not parse but contains `@` is not prefilled at all), whether the file has content (the writer's backup rule), which hand-written password key is present, and the keychain account Coda wrote (only with `password_keychain = true` and a parseable URL and username from the file, never the env overrides). `navidrome_env_overrides` names the `CODA_NAVIDROME_*` variables that are set.
- `secret_store` — the only user of `keyring-core` 1.0 and its store crates (the `keyring` 4.x ecosystem, see below): `SecretStore::{system, get, set, delete}`, service `coda`, account `<username>@<host>[:<non-default port>]`. Backends: `apple-native-keyring-store` (login Keychain) on macOS, `zbus-secret-service-keyring-store` with `crypto-rust` on Linux (pure-Rust D-Bus and crypto: no libdbus headers or OpenSSL at build time; a running Secret Service at run time). Store errors are reduced to `SecretError::{Missing, Unavailable, Denied, Failed}` because the crates' own errors can name the account or carry secret bytes. The process-wide store is cached once opened (a failed open is retried). Unit tests and the `mock-secret-store` cargo feature (pty smoke runs only) use `keyring-core`'s in-memory mock store instead, so no test touches the real keychain; a feature build calls it "test store (in memory, not saved)" on screen and logs a warning when it opens it. Not the `keyring` crate itself: its v1 facade always installs the platform store and cannot be pointed at a mock, and its docs recommend `keyring-core` plus chosen stores for applications that need that control.
- `onboarding` — pure setup state machine (first run, or a redo for `coda --setup`): screens Welcome → Music folder (skippable) → "Navidrome?" (Esc back to the folder) → server form (URL, username, password; skippable) → Ready (summary, save) or Nothing (both skipped, exit 0 without writing). Abstract `Input`s and driver `Response`s in; `Request::{CheckFolder, Ping, Save}` out with ids, so stale or abandoned answers are ignored. The server form is a separate `ServerForm` (URL, username, masked password, focus, inline error; Enter moves on or submits a validated `Server`, Esc cancels), shared with the in-app settings, as is `navidrome_blocked_by` (the env-override rule). URLs without a scheme get `https://` and are validated with `parse_base_url`. The password is a `Password` and is shown masked (`LineInput::masked`); `Debug` of the state, requests and servers is redacted. Quit (Ctrl-C, hinted on every screen) is ignored while saving, so the process never stops between the keychain write and the config write. `Onboarding::redo(Redo, suggestion)` prefills the folder (input capped at 4,096 chars), URL and username (never the password; the form focuses the first empty field); a value the input cannot hold exactly (too long, control characters) is left out with a note, and a redo with nothing to prefill uses the first-run welcome and the `~/Music` suggestion. It and carries what is set outside Coda by name: `CODA_MUSIC_DIR` or the `MUSIC_DIR` argument, the set `CODA_NAVIDROME_*` variables, and a hand-written `password`/`password_command`. In a redo, skipping a source removes it, and skipping Navidrome without a folder (from the question, the form's Esc or `s` after a failed save) returns to the Navidrome question with "Keep at least one source" instead of the Nothing screen; Ctrl-C leaves without changes. While `CODA_NAVIDROME_URL` or `CODA_NAVIDROME_USER` is set without `CODA_NAVIDROME_PASSWORD` (`Redo::navidrome_blocked_by`), a redo never opens the server form (no ping, no keychain write: startup would look the password up under the env-merged account); it names the variables and offers `k` keep `[navidrome]` as it is (`Request::Save { keep_navidrome }`) or `n` remove. Removing Navidrome while some but not all `CODA_NAVIDROME_*` variables are set shows on Ready that they must be unset too (startup would otherwise report a partial configuration). First run cannot see these variables (any of them makes the config a "partly configured" error, not `NoSource`).
- `setup` — the setup driver, run by `main` when `Config::load` returns `NoSource` and stdin and stdout are terminals, or for `coda --setup` (`Context::redo` with a `RedoContext::from_start` built from `read_for_setup`; a folder given as argument or `CODA_MUSIC_DIR` is validated first, as on a normal start, and without a terminal on both stdin and stdout it is a usage error, exit 2), before mpv is spawned. Its own short TUI session with the same discipline as `app::run` (panic hook chained to and then restored to the previous hook, `ManuallyDrop` terminal released explicitly, restore on every exit including SIGTERM/SIGHUP/SIGINT). Folder checks and the save (keychain first, then config) run on blocking threads, the ping with a temporary `navidrome::Client` on a Tokio task; each request answers exactly once through a drop guard. If the config write fails after the password was stored, the new entry is deleted again (best effort), unless it is the previous config's own entry (unchanged account, overwritten in place). On a redo, once the config is written, the keychain entry Coda wrote for the previous config is deleted best effort when the account changed or Navidrome was removed (not when it is kept); a failure is logged by kind only and does not fail the save. A terminating signal during a save waits up to 5 s for it to answer before leaving. Logs only kinds and outcomes. The keychain-then-config sequence (`store_then_write`) is shared with the in-app settings through `save_navidrome`, which writes only `[navidrome]` and returns the file's `scrobble`; the drop guard `Reply<R>` and `ping` are shared too. Afterwards `main` reloads the config with `Config::load` (with the same music directory argument) and continues the normal startup. Known gap: Tokio's signal handlers stay installed once setup registered them, so a SIGTERM/SIGHUP/SIGINT that arrives after setup ends but before `app::run` listens again (keychain read, mpv start) is swallowed instead of ending the process.
- `config_writer` — writes the setup's choices (`write`), or for the in-app settings only `[navidrome]` (`write_navidrome`: `music_dir` and `scrobble` are kept by value from the existing file, which must parse, else nothing is written; returns the backup and the `scrobble` setting; removing `[navidrome]` from a file without a `music_dir` is refused, `NO_SOURCE_LEFT`, so the file always keeps a source): `music_dir` as typed (`~/` kept), `[navidrome]` `url`, `username`, `password_keychain = true`, behind a comment header; hand-escaped TOML basic strings. `NavidromeSection::{Remove, Keep, Write}`: setup decides every other setting the file can hold, so only `scrobble` is kept from an existing file, plus, with `Keep`, every `[navidrome]` key by value (the existing file is re-read strictly, unknown keys rejected as by the loader; if it cannot be parsed, or no longer has `[navidrome]`, the save fails instead of losing the section). Atomic 0600 temp file + fsync + rename, missing parent created 0700 (a relative `CODA_CONFIG` without a directory means `.`); a symlinked `config.toml` is replaced by a regular file and its target left unchanged; an existing file is hard-linked to `config.toml.bak.<secs>` first unless it holds only whitespace and comments, or is byte for byte what Coda writes for its own settings (`needs_backup`: Coda's header and only keys Coda writes; another comment, a hand-written `password`/`password_command` or a changed layout still gets a backup), so repeated saves do not pile up backups.
- `settings` — pure state of the in-app Settings overlay (`,`), no I/O and no Ratatui. A `Context` built by `main` says what it shows and may change: the config path, the music folder of this run and where it came from (`CODA_MUSIC_DIR` or the argument), the `CODA_NAVIDROME_*` variables that are set, and who owns Navidrome (`Navidrome::{NotConfigured, Coda { url, username, account }, Outside { by }}`; Coda-owned means `password_keychain = true` and no `CODA_NAVIDROME_*` variable; `by` names the variables or the hand-written `password`/`password_command` key, never values). Overview keys: `c` Connect (not configured), `e` Edit (Coda-owned; prefilled except the password), `d` twice within 3 s Disconnect (Coda-owned; refused unless the config file has a `music_dir`, `Context::file_has_music_dir`, which `main` reads from the file when the run's folder came from the argument or `CODA_MUSIC_DIR`; the writer enforces the same rule), Esc/`,` close. The form is `ServerForm`; a submit emits `Request::Ping`, its success `Request::Save` (with the previous Coda account), a disconnect `Request::Disconnect`; ids filter stale or abandoned answers (Esc stops waiting for a ping). Keys are ignored while saving, so the overlay never closes between the keychain and the config write. Connect and edit are refused (with the variable names) under the env-override rule, or without a config location. A successful save or disconnect returns a `Change` for the app. `Debug` redacts URLs, users, accounts and paths.
- `model` — `Track`, `TrackSource::{Local, Navidrome { song_id }}`, metadata with fallbacks and length caps. `album_artist` comes from lofty's `ItemKey::AlbumArtist` for local files and from OpenSubsonic's `displayAlbumArtist` for Navidrome songs (`None` when the server does not send it).
- `queue` — pure ordered queue addressed by `QueueEntryId`, capped at 10,000 entries: append/insert, move up/down, clear, shuffle-after-current with injected randomness (small SplitMix64 `Rng` seeded from `getrandom`), and a revision counter for change detection. "Play next" (`insert_next`, `Placement::Next`) inserts after the current entry, behind the last entry it inserted (`next_anchor`), so consecutive `A`s keep press order; the anchor is data on the queue, not saved, and is forgotten when `current` changes (playback advancing, `p`, playing another entry, play now, removing the current entry) and on shuffle and clear. Appending, moving and removing other entries keep it; if the anchor entry is gone or now comes before the current one, inserts go right after the current entry again. Several tracks go in as one splice (`insert_all_next`, `Player::enqueue_all`). Without a current entry `insert_next` appends (and the status line says "Added").
- `player` — pure coordinator: user intents and `PlaybackEvent`s in, `PlayerCommand`s out (loads carry the `TrackSource`). Credential-free. Auto-advances only on EOF/error of the current `LoadId`. `RepeatMode::{Off, All, One}`: a repeat reload or wrap is a fresh load, so stale-event filtering is unchanged. A load counts as *proven* once it reports ≥ 1 s of position after `Started`; an unproven EOF is treated like a failure (it advances instead of repeating), and failures in a row stop playback once they reach the queue length, so repeat can never hot-loop. Consequence: tracks shorter than about 1.25 s are never repeated.
- `resolve` — turns `PlayerCommand`s into backend `PlaybackCommand`s: local path → `PlaybackTarget::File`, Navidrome song → freshly signed `PlaybackTarget::Stream`. An unresolvable load is fed back to the player as `TrackEnded { Error }` so the queue advances; when Navidrome is not configured, runs of remote entries are skipped in one pass to the next local entry. Shared by the app and real-mpv tests.
- `navidrome` — Subsonic client (`reqwest`/rustls): salted-token auth with a fresh salt per request, ping/getArtists/getArtist/getAlbum/search3/getPlaylists/getPlaylist/getAlbumList2, playlist writes (createPlaylist, createPlaylist with `playlistId` to replace the songs, updatePlaylist to add or rename, deletePlaylist; one request each; an empty replace is refused unsent, `Error::EmptyReplace`, because Navidrome ignores it), stream URL signing. `getPlaylists`/`getPlaylist` also give `Access` (`owner`, capped, and OpenSubsonic's `readonly`; editable only by an owner equal to the configured username, compared case-insensitively, and not flagged). **Write transport:** `Client::transport` asks `getOpenSubsonicExtensions` once per client (clones share a `tokio::sync::OnceCell`); if it lists `formPost`, writes are `application/x-www-form-urlencoded` POSTs to the bare endpoint URL with the auth parameters in the body, at most 512 KiB (`MAX_POST_BODY_BYTES`, under nginx's default 1 MB); otherwise GETs whose URL must stay within 8 KiB (`MAX_GET_URL_BYTES`). Only a definite answer is remembered: the list, a Subsonic error other than rejected credentials, or HTTP 400/404/405/410/501 (a server without the endpoint: GET). Anything else (network errors, rejected credentials, 401, 403, 408, 429, 5xx, redirects, an unreadable body) fails the write and is asked again next time. A request over its limit is refused before sending (`Error::RequestTooLarge`); `id_batches` splits id lists into requests that fit, computing the exact encoded size (salt and token have fixed lengths). Bodies and URLs are never logged. **What Navidrome does** (checked in its source, commit `ec2e0a9`, 2026-10-23): `getOpenSubsonicExtensions` is public and lists `formPost` v1; a `postFormToQueryParams` middleware on every endpoint parses the form body (10 MB `MaxBytesReader`) into the query, so auth in the body works; endpoints are registered for every method, so GET works too; `getPlaylists` returns all of the user's playlists plus other users' public ones, with `owner` (the username) and `readonly` (true for other users' playlists and smart playlists); `createPlaylist` with `playlistId` replaces the tracks in the given order, duplicates kept (owner or admin only; smart playlists refused) and returns the playlist; `updatePlaylist` deletes the 0-based `songIndexToRemove` positions before appending `songIdToAdd`; owner or admin only. **Missing files:** `getPlaylist` loads only entries whose media file is not missing (`GetWithTracks(…, includeMissing=false)`: `Where(Eq{"missing": false})`), but `songIndexToRemove` deletes by stored position (`playlist_tracks.id = index + 1`), which counts every entry; so an index from the shown list can name another entry, and Coda never removes by index. A replace (`createPlaylist` with `playlistId`) deletes every row and inserts the given ids, so **removing a song or saving a new order drops the entries Navidrome hides**: missing files, and (filtered when the playlist is loaded, by `applyLibraryFilter`) songs in libraries the user cannot access. Navidrome's `songCount` counts all of them (`refreshCounters`, run on every track change, filters neither), so `PlaylistSongs::hidden_entries` compares `songCount` with the entries returned: more stored is `Hidden::Some(n)`, fewer stored is `Hidden::Suspect` (the counts disagree, so hidden entries cannot be ruled out), no `songCount` is `Hidden::None` (no warning; the drop above still applies). With hidden entries, `d` and `w` first warn, instruction first so a narrow status line keeps it ("Press w again to save: this also removes N entries Navidrome hides (missing files or other libraries)") and act only on a second press within 3 s with nothing in between (`EditArm::Remove`, `EditArm::SaveOrder`); `J`/`K` stay allowed. The confirmed count travels with the edit (`hidden`, `Hidden::bound`, `Suspect` as unbounded), and the stale check refuses (`Stale`) when the refetched playlist hides more than that, so a replace never drops more than the user confirmed. A replace with no ids leaves the tracks unchanged (`Put` only rewrites tracks when there are some), so the last song cannot be removed this way. Admins can therefore change other users' playlists on the server, but Coda only edits the user's own. Timeouts, 8 MiB streamed body cap (24 MiB for `getPlaylist`: a realistic OpenSubsonic entry with several artists, contributors and a long path is about 2 KB, so 10,000 entries are about 20.6 MB), redirects disabled, URLs stripped from errors, lenient parsing of untrusted responses. `getAlbumList2`'s `type` comes from the closed `AlbumSort` enum and `size` is clamped to 1..=500; a page reports how many items the server sent (`AlbumPage::served`, usable or not), so skipped items still advance the offset and a short page is detected. `getPlaylist` likewise reports `PlaylistSongs::served`, so a playlist cut at the entry cap is shown as "first 10,000 of N". Each call parses its own reply type (`api::Reply`: `status`, `error` and its one section; every other key is drained), and all objects built from one response share a budget of 100,000 (`MAX_RESPONSE_OBJECTS`, a thread-local reset by a guard around each synchronous `api::parse`, also on error or panic), because lists nest four deep (`artists.index[].artist[].album[].song[]`) and per-list caps alone multiply; objects past it are drained. Parsing never builds a `serde_json::Value`, in any section: sections and list items are read straight into typed structs (`ObjectSeed` through `next_element_seed`; an item that is not an object is drained), every field goes through a visitor that accepts only the scalar it expects and drains arrays and objects with `IgnoredAny`, unknown keys are skipped unparsed, strings are copied only up to the 512 chars kept and oversized ids not at all, and lists keep a capped number of items (500 albums per page, 10,000 playlists, 10,000 playlist entries, 50,000 for any other list), draining but counting the rest. A duplicate key Coda reads fails the response. Measured peak RSS against the cost of just reading the body: nested empty objects (index → artist → album → song) fill the budget and add about 19 MB, at 8 MiB through `getArtists` and at 24 MiB alike (before the budget: 435 MB and 1.31 GB); the same 24 MiB body through `getPlaylist`, which drains `artists`, adds 0.07 MB; a 16 MB body whose one entry holds a nested array of small objects (in a known field or an unknown key) adds about 0.1 MB (about 1.5 GB with `Value`-based items); 10,000 realistic 2 KB entries (20.6 MB) add 4.3 MB. Song counts and durations of albums and playlists saturate. `Password`, `StreamUrl` and `Client` redact in `Debug`/`Display`.
- `playback` — boundary types and `PlaybackHandle` (unbounded commands, bounded events). The visualizer crosses it as `PlaybackCommand::SetVisualizer(bool)` in and backend-neutral `PlaybackEvent::Visualizer { load, frame }` (a `VisualizerFrame`: L/R levels and 7 bands at 63 Hz–16 kHz, each `0.0..=1.0`, a band `None` when the track cannot contain it) and a one-time `PlaybackEvent::VisualizerUnavailable` out; nothing mpv-specific reaches the app.
  - `mpv::visualizer` — pure: the filter graph (`GRAPH`, one constant: `@vizfmt:format=channels=stereo,@viz:lavfi=[…]`, the M6 spike's recommended graph with 2048-sample chunks; band-pass per band on a mono downmix, `astats` per channel, an `aeval` time-code channel `mod(t,32)/32`, `pan` back to stereo), defensive parsing of `af-metadata/viz` (dBFS strings, length-capped; NaN, infinities and missing keys are silence; a sample without a usable time code is dropped; extra keys ignored), a play clock extrapolated from `time-pos` (held while paused, at most 1 s ahead), the time-code aligner (readings wait until the position reaches them; repeats of the last polled time code, readings from before a seek or load, and readings more than 5 s ahead or 0.25 s behind are dropped, and so are queued readings that end up more than 5 s ahead of the position; at most 128 queued; only the newest due reading is sent), and attach/poll state. Sending a seek only drops the poll already out. mpv's own `seek` event holds positions and readings back until `playback-restart`, because mpv answers `success` to a seek it does not perform (a non-seekable stream) and then sends neither event. Only the start of the most recently sent load counts, and the graph is added once its events have been delivered. The graph is added with `af add` the first time the visualizer is wanted while a track plays (not paused, no load in flight) — never at spawn or while idle, where mpv accepts a bad graph unchecked and then fails every file. An error reply makes it unavailable for the session (reported once, never retried). While hidden it stays attached and is removed (`af remove @vizfmt,@viz`, before the `loadfile` or `stop`) only at the next load or stop, because removing it mid-track skips 23–55 ms. If a track fails while the graph is attached and before it ever produced a reading (an `af add` that raced the end of a track and landed while idle), the graph is removed and reported unavailable. Bands at or above half the track's sample rate (`audio-params/samplerate`, observed) are `None`.
  - `mpv::protocol` — JSON IPC encode/decode.
  - `mpv::state` — pure entry-id ↔ `LoadId` mapping, load serialization and collapse, event buffering, redirect and unrequested-entry handling. A `ReplyWatchdog` records when each request was handed to the writer; a reply overdue by 10 s means mpv is hung. Gaps of more than 1 s between the driver's checks (a blocked consumer, a slow pre-check, a suspended process) are excused, and `Instant` does not advance during system sleep. Replies are not always immediate: after `end-file eof` on the last entry, mpv blocks while it drains its audio buffer (observed up to about 2 s on real devices), and the timeout covers that. A hung idle mpv is noticed only at the next command.
  - `mpv::process` — argv (incl. `--network-timeout` and always `--audio-channels=stereo`, so the visualizer graph has one fixed layout and adding it never changes what is heard; mono plays as L = R at −3 dB, surround is downmixed by mpv), private socket directory, spawn with `CODA_NAVIDROME_*` removed from the environment, connect retry.
  - `mpv` (driver) — async task: reader loop plus a separate writer task, file pre-check (files only; streams skip it and are never trace-logged), shutdown with `ShutdownOutcome`. When the watchdog trips it takes the crashed-backend path (`BackendExited("mpv stopped responding")`, bounded kill and reap, socket dir removed); there is no automatic restart. A rejected `set_property volume` becomes `PlaybackEvent::VolumeRejected { volume, reason }`, so the player drops that request and keeps the user's saved preference. `MpvOptions` (program path, `--ao=null`, reply timeout, a replacement visualizer graph, extra args) is internal and only used by tests; `spawn_backend` always uses the defaults, and a test checks the graph is never a spawn argument. The visualizer is polled, not observed: while it is wanted, attached and a track plays unpaused, a deadline branch in the driver's `select!` wakes it at most every 33 ms, sends the due reading as an event and sends one `get_property af-metadata/viz` if none is in flight (polls go through the same watchdog; they are logged only at `trace`). Hidden, paused, stopped or unavailable, the branch is disabled and costs nothing.
- `session` — `state.json` in the state dir: versioned JSON of queue (source + metadata, never URLs or credentials; `album_artist` is optional and left out when absent, so files with and without it are both version 1), current index, volume, repeat, and `visualizer` (written only when on, so files with and without it are both version 1; any value other than `true` reads as off, without rejecting the file). Loaded before the TUI with a 16 MiB cap, `O_NONBLOCK` open + fstat, typed deserialization with a capped sequence visitor; invalid files are quarantined as `state.json.bad.<secs>` (never overwriting) and the user is told once. Saved atomically (temp file 0600, fsync, rename, dir fsync) by the app's `Saver`: debounced 2 s after a revision change, one write at a time on `spawn_blocking`, and a bounded final save at exit, run alongside backend shutdown. Restore never auto-plays.
- `line_input` — the shared single-line input (256-char cap by default, 4,096 for the setup's folder, control-character filtering, newline/tab → space, paste) used by local and Navidrome search and the setup form, with a masked display mode for the password.
- `library::search` — synchronous case-insensitive substring search over title, artist, album and the path relative to the music root, run on submit; shows the first 1,000 matches plus the total; results are a snapshot shown as an overlay, so the browse position is kept. Accepted deviation from the M3 brief: about 14 ms worst case for 50k tracks in release (Apple silicon), roughly one frame, once per submit. Move it to `spawn_blocking` if libraries or hardware make it noticeable. No Unicode normalization, so an NFD path does not match an NFC query.
- `navidrome::scrobble` — the pure `Listen` rule, one per load of a remote track: "now playing" on `Started`; one submission at 50 % of the duration or 4 min, whichever comes first, counting only position steps of (0, 2 s] while not paused, skipping tracks under 30 s or of unknown duration; `time` is the wall-clock time captured at `Started`. The `Scrobbler` is a single worker task with a bounded queue (16; overflow is dropped and logged), separate from the browse fetch semaphore, so requests stay in order and never take browse capacity. Failures are logged by `detail()`; only the first is shown. Config `[navidrome] scrobble` (default true).
- `library::scan` / `library::tree` — blocking-thread scan with incremental batches; directory browse tree. The tree owns every track once (`TrackId`, insertion order, stable because the library only grows); its folders, the tag index and playlists hold ids, not copies. The scan also collects `*.m3u`/`*.m3u8` files under the same rules as audio (hidden skipped, file symlinks to regular files followed, folder symlinks never walked, non-UTF-8 paths skipped; not counted as skipped), at most 1,000; after the walk it reads each on the scan thread and sends `ScanEvent::Playlist` after every batch and before `Finished`.
- `library::m3u` — pure `parse` (at most 1 MiB, cut on a line boundary, and 10,000 entries, with a `cut` flag; UTF-8, decoded lossily when invalid; BOM, blank and `#` lines skipped, `#EXTINF` ignored; LF, CRLF and CR) and pure `resolve` (no file-system access): URLs (`scheme://…`, or `file:`) are skipped, while names like `AC:DC/x.mp3` resolve normally; `\` is mapped to `/` first (Windows playlists), and a drive path (`C:\…`) counts as outside; relative entries join the playlist's folder and may start with `..` (exact, because the walked folder and the canonical root contain no symlinks); `..` after a name, or in an absolute entry, is refused (it could pass through a symlinked folder); the result must lie below the canonical music folder. Known limitations: matching is case-sensitive and without Unicode normalisation (NFC vs NFD), and absolute entries must use the canonical music-folder path. `read_playlist` opens with `O_NONBLOCK | O_NOCTTY`, checks for a regular file on the handle and reads at most the cap plus one byte. Entry paths are never logged.
- `library::tags` — `TagIndex`, updated per track as batches arrive: artist = album artist, else artist, else "Unknown artist"; album = (artist, album tag), else "Unknown album" under the artist. Keys are lowercased (tags are already trimmed); the most common spelling is shown (at most 8 spellings counted per key). Sorted lists (artists A–Z, each artist's albums A–Z, all albums by name or by artist, unknowns last) are kept by binary-search insertion; album tracks sort by disc, track, title, path.
- `library` — `Library` aggregates the tree, the tag index, a path → `TrackId` map and the playlists (`LocalPlaylist`: matched ids in file order with duplicates, a missing count covering unmatched, outside, unsupported and URL entries, and the `cut` flag; A–Z). A playlist is matched when its event arrives, after every track. Measured in a release build on an Apple-silicon Mac (`fifty_thousand_tracks_index_without_blocking_a_frame`): 50,000 tagged tracks in batches of 200 take about 75 ms in all with the worst batch about 2.6 ms; 50,000 untagged tracks in one folder (the worst shape: one folder, one album) about 340 ms in all, worst batch about 2.8 ms; matching a 10,000-entry playlist about 1.4 ms. So all of it runs on the loop, a batch or a playlist per event.
- `library::browse` — `LocalBrowser`, pure local navigation over a `Library`: a stack rooted at a static Home (Playlists, Folders, Artists, Albums), then folders, Artists → Artist → Album, Albums (`AlbumOrder::{Name, Artist}`, `o` cycles and keeps the selected album; Home reopens the last order), Playlists → Playlist. Separate from the Navidrome browser (nothing is fetched). The selection is kept on its item by `RowKey` across scan events (not in Home or a playlist, which do not change and may hold a track twice); `h` re-selects the row that opened the view left. `a`/`A` take the selected track, folder (browse order), artist (albums A–Z, each in track order), album or playlist; Home rows add nothing.
- `app` — App state and the single `tokio::select!` loop (terminal input, playback events, scan events, SIGTERM/SIGHUP/SIGINT, 250 ms tick); terminal lifecycle and the panic hook. Every exit runs a bounded backend shutdown, then restores the terminal.
- `visualizer` — pure display state (`Meter`): the smoothed bars of one load. A louder reading moves a bar 70 % of the way at once; a quieter one lets it fall at most 1.6 of full height per second (the step capped at 250 ms, so a stall does not drop it at once). Another load starts from zero.
- `app` and the visualizer: `v` (provisional, settled in M7) flips the setting, saves it with the session and sends `SetVisualizer`; a restored "on" is sent at startup. The backend is told `SetVisualizer(true)` only while the visualizer is shown *and* drawable: the last frame had room for it (at least 20x16) and no overlay covered it (help, settings, the picker, the name prompt; a text input does not count). After each full draw the loop passes the frame's answer to `App::set_visualizer_drawable`, so nothing is polled for a visualizer nobody sees. Readings update the `Meter` only while shown, drawable and the current load is playing; without a reading for 300 ms (buffering, a seek mpv did not perform) the 250 ms tick lets the bars fall; pausing, stopping, hiding or changing track resets it to silence (the bars drop at once rather than decay). A reading marks only the visualizer dirty: the loop then copies the last full frame (kept only while the visualizer is shown), draws the visualizer into it and applies it (`ui::render::redraw_visualizer`), so the terminal receives just the changed cells and the rest of the UI is not rebuilt. That path is used only when nothing covers the visualizer and no cursor is shown (help, settings, picker, a text input); otherwise readings wait for the next full redraw (the 250 ms tick). `VisualizerUnavailable` shows "Visualizer unavailable" once, and again on `v` while it stays unavailable.
- `ui::settings` — the Settings overlay in the setup's centred panel (`ui::onboarding::{Panel, draw_panel, server_form}` are shared): overview with music folder (and where it is set), Navidrome status from the app's `Connection` ("Connected as user @ host", "Connecting as…", "Not connected: <error>", "Not configured"), an outside-Coda note naming the source, notices and key hints; the form with the store name, spinner while connecting or saving, inline errors.
- `ui::onboarding` — setup screens (one centred panel; typed text sanitized and tail-truncated, password masked, spinner while busy) and the key → `onboarding::Input` mapping. In a redo: its own welcome text and hints ("Esc no local folder", "n remove"), notes naming the outside settings on the folder and server screens, and on Ready "removed" for a dropped source, a warning that saving replaces a hand-written `password`/`password_command`, and that the current file is kept as a backup.
- `ui::keymap` / `ui::render` / `ui::help` — key-to-action mapping per focused panel; Library, Queue, now-playing bar and status line; the visualizer (3 rows inside the now-playing box, below the progress line, only on screens of at least 20x16: seven band columns of `▁`–`█`, three columns wide when the visualizer area has at least 42 columns, else one, and an L/R meter of `▏`–`█` on the right when it fits; silent but laid out while not playing; shape carries the meaning, so it reads the same under `NO_COLOR`, and it uses only the 16 basic colours); help overlay (22 lines, so it fits 80x24 without scrolling); the playlist picker (only visible rows built, a note while loading, on failure, or without own playlists) and the name prompt (end of the text with the cursor, a hint) as centred boxes. Both library panel titles are the path below Home (`Local (scanning…) › Albums (A–Z)`, `Navidrome (connected) › Albums (newest)`), cut at the start when too long; paged lists show a "Loading more…" or "Could not load more — r to retry" footer; the renderer reports the visible list rows back (`ViewState::remote_rows` → `App::set_remote_rows`). Untrusted text is sanitized (control and bidi characters) and truncated by display width with bounded work. Library and Queue panels keep a persistent scroll offset and build only the visible rows, so frame cost does not grow with list length.
- `navidrome::edit` — playlist edits as small sequential jobs: `EditOp::{Create, Add, Rename, Delete, Remove, Replace}` carried in an `EditRequest` (generation and id), `run` performs its requests in order, `spawn_edit` runs it on a Tokio task and answers exactly once through a drop guard (`Error::Aborted` if cancelled or panicked). `Create` sends the first batch with `createPlaylist` and the rest with `updatePlaylist` adds; `Add` batches likewise. `Remove` is a `Replace` of the shown list without that entry (see the missing-file note above; an index past the list is `Stale`, an empty result `EmptyReplace`). Both first refetch `getPlaylist` and compare the song ids in order (and that nothing was skipped or cut); on any difference nothing is written (`EditResult::Stale`). A replace (and so a removal) is never split (a partial replace would lose songs): if it does not fit one request it is refused before the refetch. A failure after some requests succeeded is `Partial { created, added, error }`. There is no server-side precondition, so a change between the refetch and the write (milliseconds) is not detected.
- `navidrome::browse` — pure remote browse state (`Browser`), owned by one client `Generation` that its `FetchRequest`s and `FetchResponse`s carry; a response from another generation is ignored (request ids restart with each browser): navigation stack of views rooted at a static Home (Playlists, Artists, Albums; fetches nothing), then Artists → Artist → Album, Playlists → Playlist (songs in playlist order, duplicates kept), Albums (one view per `AlbumSort`, `o` cycles), plus Search; session cache keyed by `Resource`, at most one in-flight request per resource, FIFO enqueue jobs (song, album, playlist, artist; each with a `Placement`) completed strictly in press order, single-line search input. Album lists are paged in one place, `Paging` per sort: `getAlbumList2` pages of 500 (`Resource::AlbumPage`), joined in the cache under `Resource::Albums(sort)`; the next page is requested when the selection is within a screen (rows reported by the renderer) of the end, until a short page, a full page that adds no new album (each list keeps the ids it holds and skips repeats, which also stops a server that ignores `offset`), or 50,000 offsets; at most one page request per list is in flight, and a response is applied only if it is that request; a later page that fails shows a footer and is retried with `r` (otherwise `r` starts the list over, after any page in flight has answered and been dropped). The random order is a single page of 500 and never cached: it is dropped when no view shows it, and reopening it or `r` reshuffles. A playlist cut at the entry cap says so in its title and in the status line when added. Emits `FetchRequest`s as data; `spawn_fetch` runs them on Tokio tasks under a 4-permit semaphore, with background enqueue jobs limited to 2 in flight so browsing is never starved. A drop guard guarantees every fetch answers exactly once (`Error::Aborted` on panic/cancel). **Playlist editing** (the browser knows the username, `Browser::for_user`): edits are queued and handed out one at a time (`take_edit_requests`); `handle_edit_response` (same generation, the running edit's id) builds the status message and reloads: the Playlists list and the affected playlist are dropped from the cache and, if a view (or the picker) shows them or a request for them is in flight, fetched again with a new request that supersedes the one in flight (a superseded answer may predate the change, so it is neither cached nor shown; a superseded failure does not fail jobs). "Add to playlist" reuses the enqueue jobs: a `Job` has a destination, the queue (`Placement`) or a playlist (existing, or new with a name), and a playlist job becomes an `Add` or `Create` edit in its turn (at most 10,000 songs, with a note). The picker (`Picker`) shows "New playlist…" and the user's own, unflagged playlists A–Z, fetching the Playlists list if needed; it remembers the selected playlist's id, keeps the old choices listed while the list reloads (so Enter always acts on a row the user sees) and re-selects by id afterwards (row 0 if it is gone); the name prompt (`LineInput`, 256 chars, control characters filtered; a blank name cancels) serves new playlists, the saved queue (prefilled `Queue <local date>`, from `localtime_r`, UTC if that fails; `localtime_r` may read `TZ`, which is sound because Coda never changes its environment at runtime) and renames (prefilled; an untouched prefill, even one cut at 256 chars, or the same name sends nothing). Reordering changes a `Draft` (one at a time: the base ids and the reordered songs), shown instead of the cached list with "(modified)" in the title; moving back to the original order drops it; leaving or reloading its view is refused; `w` sends one `Replace` and ties the draft to that edit's id: while it runs, moves and `Esc` are refused ("Saving the new order…"), and only that id's answer ends the draft (success or `Stale` drop it and reload; a failure keeps it on screen, unreloaded, so `w` retries; too large for one request says so without offering a retry), so a discard can never race the save of the same order. Index edits (remove, a new draft, `w`) are refused with "Waiting for the previous change…" while another edit of the same playlist is queued or running; removing the only song is refused (delete the playlist instead). Removal and reordering are refused on another user's or a flagged playlist (another owner is named first, as Navidrome also flags those) and on a playlist with entries Coda could not read or cut at the cap, since positions would not match the server's.
- `app` has two library sources (`Source::{Local, Navidrome}`, keys `1`/`2`) and a `Connection` state. The local source holds the `Library` and a `LocalBrowser`; without a music folder it shows "No local music directory configured" and its keys do nothing. It drains fetch requests at the top of each loop iteration and applies `FetchResponse`s from a channel branch. Bracketed paste is enabled; pastes go only into the search input, filtered like typed text.
- `app` holds the `Settings` overlay: while it is open, keys go to it (mapped by `ui::onboarding::map_key`; Ctrl-C, and `q` outside the form, quit; while a save runs the first one only warns and the second quits, the exit still waiting for the save). The loop performs its requests in `SettingsIo`: the ping on a Tokio task, save and disconnect on blocking threads (client built, keychain, config, old entry deleted), each answering once through `setup::Reply`; saves still running at exit are awaited for up to 5 s. A `Change` swaps the client in place (`App::swap_client`): the generation is bumped, a fresh `Browser` replaces the old one (started if the Navidrome source is shown; after a disconnect the Local source is shown), the connection goes back to Connecting, the listen in progress and unsent scrobbles are dropped, the current load (possibly still loading, resolved for the old server) is never reported as a listen, and `take_client_change` hands the loop the new client and generation. The loop aborts the old client's fetches (they answer `Aborted`, which the generation check drops) and gives the new client its own fetch permits (`Fetches::restart`), starts a new ping tagged with the generation (`App::handle_ping` ignores an old one) and, with `scrobble` from the file, a new `Scrobbler`, dropping the old receivers and scrobbler. Playback is not touched: the current stream plays on, and queued remote tracks resolve with whatever client is current at their next load (without one they fail and are skipped by the existing `resolve::dispatch` path). `2` without Navidrome shows the Navidrome source with "Press Enter to connect"; Enter opens the Connect form, and the other library keys do nothing there.
- `app` maps the playlist keys (provisional): `S` in the queue saves its Navidrome songs as a new playlist (local tracks left out and counted; without Navidrome or without remote songs a message); `P` in the library opens the picker (on the local source a message: only Navidrome songs can be added); in the Playlists list `N` new, `e` rename, `D` twice delete; in a playlist `d` twice remove, `J`/`K` move, `w` save, `Esc` discard. The double presses are armed like `C` (`EditArm`: the playlist, or the playlist, index and song id; 3 s; any other key disarms). While the picker is open it takes the keys (j/k, Enter, Esc/h, q); the name prompt takes them like the search input, pastes included. The loop's `EditRunner` holds the running edit (generation, id, task) and starts the next one, of any generation, only after that one has answered, so edits stay one at a time across account swaps too; edits are not aborted when the client changes (the old server's change completes; its result is dropped by the generation check). While an edit is queued or running (the browser's pending edits, or the runner's `App::edit_in_flight` flag, which `pump` sets and `answered` clears, so an edit still running for the old account after a swap counts too), the first `q`/Ctrl-C only warns ("A playlist change is being saved; press again to quit"); at exit the running edit is awaited for up to 5 s (`EDIT_SAVE_WAIT`, alongside the settings save), and queued edits that never started are dropped, logged as a count. `/` is refused over an unsaved order, like `h` and `r`.
- `app` also starts a background Navidrome `ping` after the TUI is up and reports the result in the status line; without a music directory there is no scan and the library shows "No local music directory configured".
- `main` — config (first-run setup on an interactive `NoSource`, or `--setup`; `password_command` or keychain), the settings `Context` (ownership from the loaded config and the set variables), file logging, optional Navidrome client, mpv spawn and connect, then `app::run` on an explicitly built runtime that is shut down with a 500 ms bound (also after a panic), so a stuck DNS lookup cannot delay exit. The log filter always clamps HTTP crates (`hyper_util`, `hyper`, `h2`, `reqwest`, `rustls`) and `zbus` to warn, whatever `CODA_LOG` says, because hyper-util logs peer addresses at debug and zbus's Secret Service messages carry the keychain account. There is deliberately no `log` → `tracing` bridge: the keyring crates log the account through `log`.

Only `app`, `setup` and `ui` depend on Ratatui/Crossterm. Only `secret_store` depends on the keyring crates.
