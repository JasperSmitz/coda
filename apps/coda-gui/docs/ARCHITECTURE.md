# Coda App — Architecture

What exists in the code (M1 foundation, M2 browse, M3 queue and playlists, the M4 experience slice, 2026-11-05, colour themes, 2026-11-06 (removed in 2.0 N2, ADR 0009), feedback round 1 slice B: one source at a time, play history and Home, and the 2.0 slices N1 (top bar, navigation, queue panel), N2 (the look: fixed tokens, bundled fonts, glass, Preferences with the accent), N3 (colours from the music: cover palettes, colour scopes, the page glow) and N4 (the floating player, the queue rising out of it, the cover morph into Now Playing) N5a (the page scrolling under the top bar, page headers, Search), N5b (Library's Covers / List, sorts, per-tile accents, per-track listens and Your most played) N6 (Home: Where you left off with Resume, Moods for today) and N7 (page transitions and cover morphs, Genres and Playlists as tiles, the onboarding restyle)). Proposals are marked as such.

```text
React UI ──invoke("intent", {intent})──▶ commands.rs ──mpsc(256)──▶ engine.rs (one Tokio task)
   ▲  invoke("snapshot")                                             │ Engine: Player + resolve::dispatch,
   │                                                                 │   Library + scan state, scrobble listen,
   └── events: snapshot / progress / visualizer ◀── Sink (lib.rs) ◀──┤   notices, save revision, emission
React UI ──invoke("local_*" / "navidrome_*")──▶ browse/commands.rs ──▶ BrowseHandle (shared, read-only for commands):
                                                  Library (RwLock, engine writes) + current Client, each with a generation
                                                                     │ Io: PlaybackHandle (mpv), scan rx, ping,
webview <img src="coda://localhost/cover/<token>/small">             │   Scrobbler, Saver (blocking writes), 50 ms tick
   └──▶ cover.rs (URI scheme) ──▶ coda_core::cover::load + disk cache
```

## Crates
- `coda-core` (`crates/coda-core` at the repository root, lib `coda_core`): Coda's shared engine, also used by the terminal player (`crates/coda-tui`). Additions for the GUI in M1: `cover::load` (async, one cover at a key and size; `spawn_load` now uses it), `cover::encode_jpeg`, `Library::track_id_by_path`, `logging::init_logging_at(path)`, `Drop for PlaybackHandle` (SIGTERM to a still-running mpv), and on Linux `PR_SET_PDEATHSIG` in `mpv_command`. In M4: `config_writer::{Preferences, write_preferences, read_preferences}` (music folder, `scrobble`, `[ui] cover_art`; `[navidrome]` kept as is, same backup/atomic-write rules), `playback::mpv::process::{find_program, default_program, FALLBACK_DIRS}` (`spawn_backend` looks for mpv on `PATH`, then `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`), and `Player::set_volume` now works while stopped (the request becomes the shown and saved preferred volume; mpv accepts volume while idle). In M2: `Track::album_id`/`artist_id` (Navidrome ids for navigation, set from `albumId`/`artistId`; not saved in the session), `cover_art` on Navidrome `Artist`/`Album`/`Playlist` and `artist_id` on `Album`, `TagIndex::album_of`/`artist_of` (a local track's album/artist) and `TagIndex::search` (artists/albums by name).
- `coda-core` (2.0 N3): `cover::palette` (pure: `palette(&CoverImage) -> Palette {tint, accent, accent_text, vivid}`, `BASE`) and `cover::palette::color` (`Rgba`, hex, OKLab/OKLCH, gamut mapping, WCAG contrast, `text_on`), moved from the app's `palette/color.rs`; see the root `docs/ARCHITECTURE.md`.
- `coda-core` (M3): `Queue::move_entries(ids, to)` / `Player::move_entries` (a set of entries, in queue order, moved as one block to a drop gap: before the entry now at `to`, `len` = the end; `current` and the "play next" anchor kept; no revision bump when the order stays).
- `src-tauri` (`coda-app`, lib `coda_app_lib`): the backend.

## Backend modules (`src-tauri/src/`)
- `lib.rs`: Tauri builder; registers the `coda` URI scheme, creates the main window in `setup` (`"create": false` in `tauri.conf.json`, built with `WebviewWindowBuilder::from_config`, the base colour `palette::BASE` as the native window and webview background, and the accent's initialization script (`prefs::init_script`: the accent mode, and a custom accent's colours); `PrefsStore` is managed before the window exists and also gives the lyrics index switch at start), spawns the engine in `setup`, manages `EngineHandle`, and owns the quit sequence.
- `bootstrap.rs`: `Paths` (GUI files under `<Coda state dir>/coda-app/`: `session.json`, `history.json` (play history, loaded at startup with `history::load` on a blocking thread, alongside the session restore), `coda-app.log`, `media/` for the media-controls cover; Coda's cover cache is shared; `tui_session` = the TUI's `state.json`), `init_logging`, and `start()`: `Config::load(cli_from_process(), Env::from_process())` (`CODA_MUSIC_DIR` honoured like the TUI), password + `navidrome::Client` (`config::navidrome_client`), `playback::spawn_backend()` and the session restore, run concurrently. Restore first imports the TUI's session once when the GUI has none: `session::read_valid` (coda-core; non-blocking open, regular files only, 16 MiB cap, decoded, never renames) and only a valid one is copied (`create_new`, `O_NOFOLLOW`, 0600, renamed into place); a `coda-app/.tui-imported` marker records the attempt (valid or not), so it never happens again, even after the GUI's own session is set aside. The TUI's file is never modified. Every failure becomes a `ProblemDto` (`noConfig`, `config`, `mpvMissing`, `playback`, `navidrome`); nothing panics.
- `engine.rs`: the actor.
  - `Engine` is the synchronous core: `start(sources, playback_problem, restored)`, `handle_intent`, `handle_playback_event`, `handle_scan_event`/`scan_closed`, `handle_ping`, `handle_scrobble_failure`, `tick`; outputs `Vec<PlaybackCommand>` plus queued visualizer frames and scrobble requests. Every player call goes through `resolve::dispatch` (which also re-announces the gapless next after queue edits), then `take_messages()` become notices and the save revision is checked.
  - `run` is the loop: `select!` over startup completion, intents, playback events, scan events, the Navidrome ping, the first scrobble failure, a mix's fetch results (tagged with their mix), saved-mix reads and fetch retry timer (`engine/mix.rs`), and a 50 ms tick (deferred library changes, notice expiry, session-save polling; scan events and ticks return the mix's top-up commands). After each branch it flushes: visualizer frames at once, scrobbles to the worker, a `snapshot` event if anything visible changed, `progress` if the position changed and ≥100 ms passed.
  - Startup runs as its own task, so the UI gets a `starting` snapshot immediately (a password command or keychain prompt can take a while). Intents other than visualizer visibility and notice dismissal are ignored until `ready`.
  - Session: revision based (`Player::revision`), saved 2 s after the last change, one blocking write at a time; restore never auto-plays; final save at exit bounded to 2 s. The GUI has its own session file, so it never overwrites the TUI's queue.
  - Scrobbling: the engine owns a `coda_core::navidrome::scrobble::Scrobbling` (the listen policy shared with the TUI): `started`/`progressed` after the player handles `Started`/`Position`, `player_changed` in `dispatch`, requests handed to the `Scrobbler` by the loop. The engine keeps only the notice text and the `scrobble` setting.
  - Visualizer: `SetVisualizer(true)` only while the UI says a view is visible (`setVisualizerVisible`), never after `VisualizerUnavailable`; frames are forwarded raw only for `audible_load` while playing. Smoothing/decay is the UI's job (none yet: no visualizer view in M1).
  - Live settings (`engine/settings.rs`, `Msg::Settings` → `Engine::apply_settings`, refused until `ready`): `Client` (port of the TUI's `swap_client`: new `CoverService` client, which forgets remote cover tokens and mixes a new generation into new ones so the webview never shows the old server's cached art; queue resent; `Scrobbling::client_replaced` (listen and waiting requests dropped, the current load never reported, the first failure shown again); `Player::client_changed` re-announces/reloads remote entries signed by the old client; the loop pings the new client and replaces the scrobbler), `MusicDir` (new `Library`, `Scanning`, the loop starts a new scan; dropping the old receiver ends the old scan), `CoverArt` (URLs on/off, queue resent), `Scrobble` (needs a client; `Scrobbling::switch`: a track already playing is not reported halfway). `Client`/`MusicDir` clear `noConfig`/`config` problems (onboarding).
  - `Client` and `MusicDir` also update the `BrowseHandle` (new client / new library, each a new generation; the queue is resent so local ids follow the new library).
  - Shutdown (`EngineHandle::shutdown`): `phase = shuttingDown` snapshot, wait ≤3 s for a still-running startup (else abort and await it, so a `PlaybackHandle` it holds is dropped and mpv terminated), final save, `PlaybackHandle::shutdown(2 s)`, reply.
  - Queue edits (M3, `engine/queue_edit.rs`): `moveEntries` (gap resolved from the `before` key), `removeEntries` (the playing entry removed last, so playback moves on to an entry that stays), `playNextEntries` (moved right after the current entry), `shuffleUpcoming` (`Player::shuffle_upcoming`, Coda's notice). Each goes through `Player` and then `dispatch`, which re-announces the gapless next.
  - `engine/playlists.rs`: `Msg::Playlist` for the playlist editor: `EngineHandle::notify(text)` (an edit's outcome as a notice) and `EngineHandle::queue_songs()` (the queue's Navidrome song ids in order + the number of local tracks, Coda's `save_queue_as_playlist`).
  - Play history (`engine/history.rs`, owner feedback round 1): the engine owns a `history::History`. `playTracks` carries an optional `context` (`PlayContextDto`: `album`/`artist`/`playlist` `{source, id, name?, subtitle?, coverUrl?}` or `folder {path}`); when the play replaced the queue, the context is resolved (a local id of the current generation → a stable key; a stale or unknown id records nothing; a Navidrome cover URL → its `coverArt` id through `CoverService::key_for_url`, so no token is stored) and recorded as a context play, and the queue's entries are remembered as played from it. `playLocal` records its folder or artist itself; `shuffleLibrary` and context-less plays (search results) end the remembered context. Listens: on `Started` of the current load a second `Listen` (coda-core's scrobble rule: half the track or 4 minutes, ≥30 s tracks; every source, independent of scrobbling) counts for the track's album (Navidrome `albumId`; local `TagIndex::album_of` → stable key) and, if the entry came from the remembered context, that context (once per key), and (2.0 N5b) for the track itself (`heard_track`: a local track by `history::local_track_key`, a Navidrome song by its id and the current server with the row it shows; none for an entry queued before a server change). Saved like the session: 2 s after the first unsaved change (`HistorySaver`, one blocking write at a time, back-off on failure up to 60 s), and once more at quit, alongside the final session save (same 2 s bound). Navidrome history is per server: the engine keeps the current client's `history::server_id` (set at start and on every client swap) and stamps it on each Navidrome context it records; Home rows and moods are read for that server only (none while disconnected), so another server never shows the old one's, and switching back shows it again. Navidrome entries already in the queue at a client swap are remembered (`other_server_entries`) and their album listens are not counted for the new server. Every history change marks the snapshot dirty; `Snapshot.historyRevision` tells Home to reload its rows. (2.0 N6) A saved mix that starts (`start_state`) is recorded as a `mix` context (`Engine::mix_context`: its id and name, a Navidrome mix with its first song's `coverArt` id); a quick mix is none. **Where it stopped**: `PlayedFrom` keeps each entry's place in the context's own order and the context's size (`QueuedOrder`, set by the play that filled the queue: `play_tracks` shuffles its (place, track) pairs itself with `shuffle_with_first`, as `Player::play_tracks` would, and plays them unshuffled; `play_local` keeps each sampled or windowed track's place in the whole context, so a large folder cut to the queue still counts from its start), so a shuffled play and Shuffle upcoming still record the album's track number; and how the UI names the context (`PlayingContextDto {source, kind, id}`: the intent's id, a folder's path joined, a mix id). `record_stop` writes a `history::Stop` (the current entry's `heard_track` key, its place, the count, the position, now) for the context (not a mix), only while something is loaded (after the end of the queue `Player::advance` leaves `current` on the last entry with no load; recording then would undo the finish), when a load of it starts (`stop_after_event`: at 0, or at the resumed position), when playback becomes paused (the player's position), just before `playTracks`/`playLocal`/`shuffleLibrary`/`clearQueue` or a mix replaces the queue, and in `take_final_history` at quit. Its stop is cleared (Resume starts over) when playback stops at the end of the queue (`Player::stopped_at_end`) on an entry of the context, or when a load outside the context starts right after one of the context's with none of its entries left after it in the queue (`context_moved_on`). `playTracks`/`playLocal` take `seekMs?` and `seekTrack?` (Resume: the stopped track's id as a `TrackDto` names it): the engine keeps a `PendingSeek` for the load the play started and, when that load's `Started` arrives (the player refuses seeks before), sends `Player::seek_absolute` only if the started entry is that track (`current_ui_track`) and the position is more than 5 s before its known end (`RESUME_END_MARGIN`); it is dropped when another load takes over (`drop_stale_seek` in `dispatch`). `Snapshot.playingContext` is the context whose entry is the queue's current one and loaded (not one played to its end), or a saved mix while it owns the queue; a saved mix restored with the session becomes the queue's context again (`adopt_mix_context`, no play recorded). The moods' requests: `HistoryMsg::Moods` hands the command the day's cached moods (if any), the scope's album listens and (Navidrome) the heard albums' genres; `SetMoods` caches the first answer of the day, refused for a server that is no longer current (the command answers `stale`). A Navidrome listen also keeps its song's genres on its album's count (`set_album_genres`).
  - `Msg::History` (`HistoryMsg`): the Home commands ask for a source's rows (`home_rows`), the cached Navidrome picks of a date, or store them (the first picks of a day stay); Library asks for a copy of the local track listens (`LocalTrackListens`, key → listens and last listen; the Most played order and an artist's top songs resolve it against the library on a blocking thread) and the current server's top songs of an artist (`NavidromeTopTracks`).
  - Mixes (M12 part 2a, `engine/mix.rs`; the rules are `coda_core::mix`'s, ADR 0008): the engine owns the mix that plays (`mix`) and a Navidrome mix still loading (`pending_mix`); each `MixState` holds an `ActiveMix`, for Navidrome a `MixFetches`, and a tag its fetches carry so results reach only that mix. The mix that plays goes on until a new one actually starts (`start_state` swaps it in on success). Every valid play request supersedes the pending mix and a saved mix still being read (`supersede_mix_requests`), whether or not it then finds songs: `playTracks`, `playLocal` and `shuffleLibrary` on arrival, `playQuickMix` once `Mix::new` accepts the recipe (and, for Navidrome, a client exists), `playMix` once the id parses and a mixes file is configured; a refused request changes nothing. Any other intent that changed the queue context (a clear, …) supersedes too; a pending mix that finds no songs or whose fetches all failed is dropped with a notice and the old mix goes on. `playMix{id}` records a read of the mixes file (`take_mix_load`; the loop reads it on a blocking thread and hands it to `mix_loaded`, which drops it when another play request came or the queue was replaced meanwhile; gone → "That mix no longer exists"; a newer mixes file → the store's "The mixes file was written by a newer version of Coda"; a rejected one → its `LoadOutcome::rejected_notice`, "Could not read the mixes file: …; kept as …", logged at warn with `kept_as`); `playQuickMix{mix}` builds the `Mix` at once (a Navidrome one for the current server). A local mix resolves its pools inline from the library (`mix::local`, a name lookup per ingredient under the read lock, like `playLocal`); a recipe that finds no songs at all is a notice and leaves the queue (and a mix playing) alone; otherwise it starts at once, replacing the mix that played (`ActiveMix::start`: 25 songs, the first played; "Playing mix <name>", "No songs for …"). A Navidrome mix is pending while it waits for its fetches: `MixFetches::due` → `take_mix_fetches`, which the loop (`drive_mixes`, after every branch) spawns with `Fetch::spawn` (the current client and the browse handle's shared fetch limit, `BrowseHandle::fetch_limit`; never under a permit), each answering once, with its mix's tag, on an unbounded channel the loop selects on (`mix_fetched` → the pending or playing mix with that tag → `MixFetches::finish`; a result for a mix that has gone, or stale, changes nothing); it starts once `settled`, failures reported as "Could not load …; trying again later" (started without them) or "Could not load the mix's songs (…)" (after `MAX_ATTEMPTS`, dropped). A retry arm sleeps until the earliest `MixFetches::next_retry` of both mixes and calls `check_mix` (which queues what is `due`). `check_mix` runs after every intent, playback event, fetch result, retry and applied library change (scan events, also ones deferred to a tick, and a new music folder): a pending mix whose queue context changed is dropped; a playing mix whose queue was replaced or cleared (`has_ended`) is dropped with its coordinator (which stops its fetches); otherwise `wants_top_up` → `top_up`, the returned commands dispatched (the gapless next is announced again), then due fetches. A local mix resolves its pools again when the library's (generation, size) changed since, at a top-up; a mix restored before the scan therefore tops up once the library has songs. A client change to another server (or none), `Finished::OtherServer`, or fetches with no client end a Navidrome mix with a notice. Mix plays are not in the play history (`played_context(None)`). Session: `Session.mix` is the mix that owns the queue (`ActiveMix::session`: a saved mix's id, a quick mix's recipe); every change of the playing or pending mix (start, end, loading, failure) arms the save debounce and forces the exit save, even without a queue change. Startup (`bootstrap::restore_mix`, blocking, after the session restore) reads a saved mix again from the file (gone → none; a newer file → none, logged; a rejected file → none, and `Mixes::notice` with the rejected notice, which `apply_startup` shows as a notice) and the engine adopts the restored queue (`restore_mix`: nothing without a queue, a Navidrome mix only on its own server). The snapshot's `mix` is `{name, id (null for a quick mix), loading}`: the pending mix (`loading: true`) if there is one, else the one playing.
- `mixes.rs` (+ `mixes/tests.rs`, M12 part 2a): the saved mixes' commands and the editor's searches. `MixesFile` (managed state) is `config::mixes_file_path` (`$XDG_DATA_HOME/coda/mixes.json`, shared with the TUI; `Paths::mixes`). `list_mixes{source}` → `[MixDto {id, name, source, ingredients}]` (the source's mixes; Navidrome: those of the current client's `server_id`; a newer file → `newer`; an unusable one is set aside by the store and lists empty); `add_mix{mix}`, `update_mix{id, mix}` → the `MixDto` as saved (cleaned by `Mix::validated`); `add_to_mix{id, source, ingredient}` → the `MixDto` as saved (`store::add_ingredient`: the ingredient appended to the mix as saved now, under the lock; `alreadyIn`, `mixFull`, `notFound`, `otherSource`); `delete_mix{id, source}` (gone is no error). `update_mix` (the whole recipe: last writer wins), `add_to_mix` and `delete_mix` are refused with `otherSource` when the stored mix's source is not the current one (another server or account since the editor opened it, or local ↔ Navidrome), checked under the store's lock (`store::update`/`store::delete`, `StoreError::OtherSource`); the mix is left as it was. `mix` is `MixInputDto {name, source, ingredients}`; a Navidrome one is made for the current server. Each store call runs on a blocking thread and re-reads, applies one change and writes atomically (`coda_core::mix::store`). Errors: `MixErrorDto {kind: invalid|notFound|otherSource|full|alreadyIn|mixFull|newer|notConfigured|failed, message}` (`full`: 500 mixes; `mixFull`: 50 ingredients). `IngredientDto` (tagged `kind`): `genre{name}`, `artist{name, id?}`, `album{artist, name, id?}`. Searches (`Result<[IngredientDto], BrowseError>`): `mix_search_genres{source, query}` (every genre for an empty query, at most 200; local names from the `TagIndex`, Navidrome the server's exact `getGenres` value), `mix_search_artists` and `mix_search_albums` (an empty query finds none; local `TagIndex::search`, at most 50, an album with its artist; Navidrome `search3` with ids, an album with its album artist, one without an artist left out). An active mix keeps the recipe it started with; an edit applies the next time it plays.
- `history.rs` (+ `history/`): the history model and file. `Context {source, server, kind, id, name, subtitle, coverArt}`; `server` (Navidrome only, required) is `server_id` (re-exported from `coda_core::navidrome` since M12, which keys mixes by it too): FNV-1a 64-bit hex of the base URL and user name (stable across runs; the file never holds the URL or user name in plain text, though a known server's id can be confirmed by hashing; the client normalises the trailing slash); `Scope` (`Local` | `Navidrome(server)`) selects what a Home view reads; local ids are stable keys: album `"<artist>\u{1f}<album>"` (trimmed, lowercased tag names as `TagIndex` groups them), artist name, playlist name, folder path joined by `/` (`/` = the root). Per-track listens (2.0 N5b): `TrackCount {source, server, id, listens, last, song?}`; a local track's id is `"<album key>\u{1f}<disc>\u{1f}<track no>\u{1f}<title>"` (lowercased title), plus `\u{1f}<file name>` (lowercased, never the path) for a track without a track number, so two unnumbered tracks of one title on one album stay apart; it survives moves and rescans, and a retagged (or, unnumbered, renamed) track starts again; a track without an album tag is not counted per track (as its album listens are not); a Navidrome song's is its song id, with `song` (title, artist, album, album artist, album and artist ids, `coverArt` id, duration, numbers; cleaned like contexts) for its row. `local_album_listens` sums an album's tracks' listens (Library's local Most played); `local_artist_top_tracks` / `History::navidrome_top_tracks` give an artist's most listened songs (Navidrome: a song with an artist id matches by that id alone, so same-name artists with other ids stay apart; only a song without one matches by its album artist or artist named like the page, ignoring case). Context kinds: `album`, `artist`, `playlist`, `folder` and (N6) `mix` (a saved mix's id). (2.0 N6) **Stops**: `Stop {source, server, kind, id, track, index, total, positionMs, at}` per context (not mixes), kept only while the context is among the plays (dropped when its last play is trimmed, and on load), `index < total ≤ 1,000,000`, the position capped at a day. **Moods**: a Navidrome album count keeps its songs' `genres` (≤8, cleaned); `MoodsDay {date, source, server?, moods: [Mood {genre, albumCount?, albums: [MoodAlbum {id, name, artist?, artistId?, coverArt?, durationMs?}]}]}`, the latest day per scope (local and each server, ≤5 scopes; ≤6 moods of ≤3 albums; a local album by its stable key, a Navidrome one by id with what its card shows). `history/moods.rs` is the pure picking: `rank_genres` (the source's genres by the listens of their albums last heard within 56 days, an album counting for each of its genres, then the rest by album count, ties by name, case-insensitive), `pick_albums` (never an album heard within 7 days or taken by an earlier mood; never-heard first in an order seeded by FNV-1a of `moods/<date>/<server or "local">` and the album key, then the least recently heard), `pick_moods` (genres in rank order with three albums to give, up to six; too few: the genres with one or two fill in, in rank order). Bounds: last 500 context plays, counts for ≤5,000 contexts and ≤20,000 tracks (least recently heard dropped); text cleaned (control characters, ≤256 chars), ids ≤4,096 chars. `history.json` (`{version: 3, plays, counts, tracks, stops, moods}`; version 1 (no `tracks`) and 2 files are read as they are and saved as version 3 with their plays, counts and tracks, their `dailies` (the 1.x Daily Picks) dropped; Navidrome entries without a valid server id are dropped on load): read with `fsio::read_regular` (regular files only, never blocking on a FIFO, ≤16 MiB); invalid JSON, an older unknown version or a non-regular file is renamed to `history.json.bad.<unix-seconds>` and the history starts empty; an unreadable file (I/O error), a newer version or a file over 16 MiB is kept and disables saving for the run so it is never overwritten; `save` never writes more than 16 MiB (it leaves out the least recently heard half of the counts, track counts and stops and the oldest half of the plays until it fits); writes are atomic (`fsio::write_atomic`, 0600). No URLs, tokens or credentials. Home resolution (`home_dto`): local contexts are looked up in the current library by key (gone → skipped) and get current ids, names and first-track covers (a local mix: its first ingredient's first album's); Navidrome contexts show what was stored, their cover through the registry; a mix only while it is in the mixes file for that source and server, with its current name; artists and folders without a cover are left out; at most 8, newest first, each with `playedAt` (the later of its last play and its stop) and its `stop` resolved (`StopDto {index, total, trackId?, positionMs}`: local, the stopped track looked up by key among the context's tracks now (album, playlist, an artist's albums, a folder's tracks, in the order `playLocal` plays them) with its current library id, or the recorded place without a track and position when it is gone; Navidrome, the song id and the place as queued).
  - `history/commands.rs`: `home_history{source}` → `{recent}` (`HomeItem`s; reads the mixes file on a blocking thread only when a mix is among them), `home_moods{source, date}` (`YYYY-MM-DD`, the UI's local day; else `notFound`) → `{today, other}` (`Mood {genre, albumCount, albums: [{id, name, artist, artistId, coverUrl, durationMs, lastPlayed, ingredient}]}`; `ingredient` is the album as a quick mix's `IngredientDto`): the day's cached moods, else picked: local on a blocking thread from the tag index (each genre's albums, every album's genres for the ranking), Navidrome with `getGenres` and then `getAlbumList2 byGenre` (≤500 albums) for the genres in rank order, one at a time within the shared fetch limit, until all six moods are full or 12 genres were fetched; one pick per server and day at a time (`Picking`: a per-key async lock, so a second ask waits and then finds the cache), cached through the engine (first answer of the day stays), then resolved with fresh listens (local albums gone from the library left out); `artist_most_played{source, id, name}` → `[{track, listens}]` (≤6, most first; local by the artist's library id, Navidrome from what the history kept, the current server's only, `name` used only for songs without an artist id). Errors are `BrowseError`s.
- `playlists.rs` (+ `playlists/`, M3): Navidrome playlist edits through `coda_core::navidrome::edit::run` (create, save queue, add, rename, delete, remove, reorder; removals and reorders are a replace after a refetch that must match the shown list, as in Coda).
  - `PlaylistEditor` (managed state) holds a `tokio::sync::Mutex` for an edit's whole run, so edits run one at a time in order (Coda's `EditRunner`); `begin_quit` waits for a running one ≤3 s (`EDIT_GRACE`) before the engine shutdown. Edits run in the command's task, never on the engine task.
  - Each edit takes the browse handle's client only once it holds the lock, so an edit queued behind another never writes to a server the user has since left (no client then: `refused`). If the client generation changed while it ran, the outcome keeps its status (the old server may have applied it) and the message ends with "(made with the previous server connection)".
  - `finish` (quit) sets a closing flag first: edits still queued are refused ("Not changed: Coda is quitting"), the running one gets ≤3 s.
  - Validation before anything is sent (`refused`): names trimmed, control characters replaced, 1–256 characters; ids non-empty, ≤256 characters, no control characters, at most `MAX_PLAYLIST_ENTRIES`; remove indices in range, no more of them than songs, and never all (`LAST_SONG`); a reorder must be a permutation (the shown order is a no-op). One removed index is an `EditOp::Remove`, several a `Replace`.
  - Hidden entries: the UI sends the `hidden` it confirmed (`HiddenDto`, `none` without a dialog); it becomes the edit's bound (`Hidden::bound`), so a server with more hidden entries than confirmed answers `stale` and nothing is written.
  - Messages follow Coda's `edit_message` (GUI wording); every outcome is returned and shown as a notice. Errors are logged with `Error::detail()` only.
- `browse.rs` (+ `browse/`): everything the browse views read.
  - `BrowseHandle` (managed Tauri state, cheap `Clone`): the local `Library` behind a `std::sync::RwLock` plus a *library generation*, and the current Navidrome `Client` plus a *client generation*. The engine is the only writer and **never waits for the lock** (`engine/library.rs`): a library replacement (start, a music-folder change in settings; bumps the library generation), each scan batch/playlist and the scan end are queued as ops and applied with `try_write_local`; while a browse read holds the lock they stay queued and are applied on the next event or the 50 ms tick (a replacement drops ops still queued for the old library). Since no writer ever waits, the engine's own reads (refs, queue DTOs) never wait either. `ScanEvent::Finished` resends the queue so restored local entries get their ids. `set_client` publishes the client at start and on every settings client swap (bumping the client generation). Both generations are in the snapshot (`browse: {library, server}`); the UI clears its Navidrome cache and resets a stack holding that source's views when one changes. Commands never touch `Player` or the engine channel.
  - Local commands run their read on a blocking thread (`BrowseHandle::local`), so long reads (search, a 5,000-album list) never run on the engine task.
  - Navidrome commands go through `BrowseHandle::fetch`: at most `MAX_CONCURRENT_FETCHES` (4, Coda's) requests at once (a semaphore), of which an artist play-all's album fetches take at most `MAX_JOB_FETCHES` (2); a result that arrives after the client generation changed is dropped as `stale`. Failures are logged with `Error::detail()` and returned as their `Display` text (never credentials).
  - `browse::track_dto` builds every `TrackDto` (queue and browse), so local tracks are named the same way everywhere.
  - `browse/dto.rs` (browse DTOs and `BrowseError {kind, message}`), `browse/local.rs` (queries over a `LocalView`), `browse/navidrome.rs` (queries through the client), `browse/commands.rs`, `browse/tests.rs`.

It runs on the command's task, never the engine actor: a local id is resolved through the `BrowseHandle` (path looked up under the library lock, the file read by `coda_core::lyrics::read_local` after it, on a blocking thread; a stale generation, an unknown id, no library or no id is `null`); a Navidrome song goes through `BrowseHandle::fetch_raw` (the browse fetch limit and stale-client rule, without `fetch`'s warn log) to `Client::lyrics` with the ref's artist and title (capped). Lyrics with no text are `null`. A failed read or request is logged at debug and rejects with a message (the view shows "Couldn't load lyrics"). Nothing is cached in the backend.
- `lyrics_index.rs`: the Navidrome lyrics index (`docs/plans/lyrics-search.md` slice 2, ADR 0007). `LyricsIndex` (inside the `BrowseHandle`, `browse.lyrics()`) owns the current server's `coda_core::lyrics::cache::Store` and its sync task (on the async runtime, never the engine actor; the file is loaded on a blocking thread). The engine calls `set_server(client, Start::Launch)` at startup (the cache loads at once, the sync starts after 30 s) and `set_server(client, Start::Changed)` on every client swap (a sync starts now; another server gets its own store, the old file is kept; `None` from a disconnect deletes the old server's file). One sync at a time: every start, stop, server change and switch-off aborts the previous task and bumps a generation in the same critical section; a finished load is installed only under that lock if its generation, its server key and the switch still match (`install_loaded`), so a load that completes after a change installs nothing. A disconnect from Preferences also deletes the configured server's file by its URL and username (`forget`), even when its client never started (no password at launch). No timer: launch, a server change, switching on and Rebuild only. Switching off aborts, deletes the file (`Store::delete_file`, so a racing save cannot bring it back) and drops the store. `shutdown()` (from `begin_quit`, before the engine's shutdown) aborts and saves within 3 s, so a quit mid-build resumes. Status: `LyricsIndexDto {state: off|noServer|loading|idle|albums|songs|upToDate|paused, pause, done, todo, songs, checked, withLyrics}` in a `watch`; `lib.rs` forwards changes as the `lyrics-index` event, at most every 250 ms. Commands: `lyrics_index_status`, `lyrics_index_rebuild`, `lyrics_index_set_enabled{enabled}` → the new status (saves the preference with `prefs::commands::save_prefs`, then applies it). The quit save writes only when the cache changed. `Paths::lyrics_cache` is `<cache>/coda/lyrics`; with none (no `HOME`, tests) nothing ever syncs.
- `dto.rs`: serde DTOs (camelCase), mirrored by hand in `src/lib/types.ts`. `playlists/dto.rs`: `EditOutcomeDto`.
- `commands.rs`: `intent(intent)` and `snapshot()`; the browse commands live in `browse/commands.rs`.
- `settings.rs`: the Preferences view's (server, folder, options) and onboarding's commands (below). Reads the file with `config::read_for_setup` + `config_writer::read_preferences` (never resolves the password); ownership like the TUI's settings: a server Coda wrote (keychain) can be edited/disconnected, one set outside Coda (`CODA_NAVIDROME_*`, hand-written `password`/`password_command`) is shown and left alone; `onboarding::navidrome_blocked_by` blocks saving a server. ## IPC contract
- Commands: `intent({ intent })`, `snapshot()` → full `Snapshot` (queue included). Settings (each rejects with a message to show): `settings_get()` → `Settings` (`configPath`, `musicDir` as written, `musicDirEnv`, `server` = `notConfigured` | `coda{url, username}` | `outside{url, username, by}`, `serverBlockedBy`, `scrobble`, `coverArt`, `problem`), `settings_test_server({server})`, `settings_save_server({server})`, `settings_disconnect()`, `settings_pick_folder()` → path or `null`, `settings_set_music_dir({folder})` (refused while `CODA_MUSIC_DIR` is set), `settings_set_options({coverArt?, scrobble?})`, `onboarding_finish({musicDir?, server?})`. `server` is `{url, username, password}`.
- Events:
  - `snapshot` (coalesced on the 50 ms tick, only when the snapshot differs from the last one sent). `queue` is `null` when the entry list (by key) did not change, so a 10,000-entry queue is not resent on every status change; the UI keeps its last queue. `browse: {library, server}` carries the browse generations. A `snapshot()` call resets this, so the next event carries the queue again (the UI applies the command's result only if no event arrived first).
  - `progress`: `{ positionMs, durationMs }` of the heard track, ≤10/s.
  - `visualizer`: `{ levels: [l, r], bands: [7 × number|null] }`, ≤30/s, only while enabled.
- `Intent` (tagged by `type`): `togglePause`, `next`, `previous`, `seekTo{seconds}`, `seekBy{seconds}`, `setVolume{volume}`, `cycleRepeat` (no notice: the repeat button shows the mode), `playEntry{key}`, `removeEntry{key}`, `clearQueue`, `setVisualizerVisible{visible}`, `playTracks{tracks, start?, shuffle?}`, `enqueue{tracks, next?}`, `dismissNotice{id}`, `shuffleLibrary` (local "Shuffle all": every scanned track shuffled, a random sample at `MAX_QUEUE_LEN`, as in Coda), `playTracks` also takes `context?` (the play history, above) and `seekMs?`, `seekTrack?` (Resume), `playLocal{context: {kind:"folder", path} | {kind:"artist", id} | {kind:"genre", id}, start?, shuffle?, seekMs?, seekTrack?}` (a genre plays `TagIndex::genre_tracks`: its albums by artist then album, each album's tracks of that genre; genres are not recorded in the play history) (`engine/context.rs`: the engine resolves the context's track ids under its non-waiting read and clones only what the queue takes: shuffled = the start first plus a random sample, else `context_window` around the start; stale ids → notice). M3: `moveEntries{keys, before}` (one block in queue order to the gap before the entry `before`, `null` = the end; named by key, not index, so a queue that changed since the UI drew it still gets the block where it was dropped; an unknown `before` moves nothing), `removeEntries{keys}`, `playNextEntries{keys}`, `shuffleUpcoming`. Unknown keys are ignored. M12: `playMix{id}` (a saved mix, read again from the mixes file) and `playQuickMix{mix: MixInputDto}` (a recipe played unsaved); see Mixes under `engine.rs`. The `snapshot`'s `mix` is `{name, id, loading}` or `null`.
- Playlist edit commands (M3, Navidrome; each resolves with `EditOutcome {status: done|partial|stale|failed|refused, message, created}`, the message also a notice): `playlist_create{name, songs}`, `playlist_save_queue{name}`, `playlist_add{playlistId, name, songs}`, `playlist_rename{playlistId, oldName, name}`, `playlist_delete{playlistId, name}`, `playlist_remove{playlistId, name, expected, indices, hidden}`, `playlist_reorder{playlistId, name, expected, order, hidden}`. `name`/`oldName` of an existing playlist are for messages only; `expected` is the song ids as shown, `songs` Navidrome song ids.
- `Playlist` DTOs carry `editable` (`Access::editable_by` the client's user; always `false` for local) and `readOnlyReason` (Coda's `read_only_reason`).
- Browse commands (all async, `Result<DTO, BrowseError>`; `BrowseError.kind` is `notConfigured` | `stale` | `notFound` | `failed`):
  - Navidrome lyrics: `navidrome_lyrics_search{query, exclude}` → the same DTO from the loaded lyrics cache (`Store::search`, at most 50, artist/album/disc/track order, leaving out the song ids in `exclude`, at most 1,000 read; rows are Navidrome `TrackDto`s built from the cached details, which went through the same cleaning as server data), with `indexing: {done, total}` (songs checked of known) whenever songs are left to check (building, waiting for the launch sync, paused), and `{0, 0}` while the cache is still loading; empty when the index is off. On a blocking thread; no server request.
  - Local: `local_artists`, `local_albums{order: "name"|"artist"|"year"|"mostPlayed"}` (year: newest first, undated last, A–Z within; most played: the history's track listens summed per album, each album's `playCount` set, never heard last; `AlbumDto` also carries `year` (the latest tagged, `Album::year`), `genre` (the first track's first genre) and, from Navidrome, the server's `playCount` and `genre`), `local_artist{id}` → `{artist, albums}`, `local_album{id}` → `{album, tracks, genres}` (`genres`: `GenreDto`s of the genres holding any of its tracks, in the order its tracks are tagged with them), `local_genres` → `[GenreDto {id, name, albumCount, trackCount, coverUrl}]` (`coverUrl`: the first album's cover, for the genre tiles; `None` from Navidrome's `getGenres` and on an album's genre links; A–Z, `TagIndex::genres`; ids `"<generation>:<n>"`, dense like artists), `local_genre{id}` → `{genre, albums}` (albums by artist then album), `local_folder{path}` → `{path, dirs, tracks}` (one level), `local_playlists`, `local_playlist{id}` → `{playlist, tracks, missing, truncated, hidden, warning}`, `local_search{query}` → `{artists, albums, tracks, totalTracks}` (tracks: `library::search`, at most 1,000; artists/albums: `TagIndex::search`, at most 50 each), `local_lyrics_search{query, exclude}` → `{matches: [{track, snippet: [{text, matched}]}], total, indexing: null}` (`Library::search_lyrics`, at most 50 in browse order, never a track the local search for the query matches; `exclude` also holds the song ids the main search returned (kept for Navidrome), at most 1,000 read, malformed ones ignored, an older generation's makes it `stale`; a separate command so the main results never wait; on a blocking thread like every local read). `tests/acl.rs` checks that `generate_handler!`, `build.rs`'s manifest and `capabilities/default.json` list the same commands. The engine starts its scans with `ScanOptions { lyrics: true }` and applies `ScanEvent::Lyrics` through the same deferred library ops as batches. Playing a whole folder or local artist is the `playLocal` intent (below), so those lists never cross IPC. Ids and queries from the UI are bounded (256 chars; a Navidrome id longer or empty is `notFound`, a query is trimmed and cut). Scan state is in the snapshot (`scan`), not a command.
  - Navidrome: `navidrome_artists`, `navidrome_artist{id}` → albums, `navidrome_artist_tracks{id}` (albums fetched in parallel within the fetch limit), `navidrome_album{id}` (`genres` from its songs' genres in tag order, each once ignoring case, with the cleaned name as id and no counts; the webview resolves each against the cached `navidrome_genres` listing for its exact value, see `lib/genres.ts`; header from `getAlbum` itself via `Client::album_detail`: name, album artist and *their* id, year, cover; a song's `artistId` is the track artist's and never used for the header), `navidrome_albums{sort, offset}` → `{albums, nextOffset}` (pages of 100, the six `AlbumSort`s, stops at `MAX_ALBUMS`), `navidrome_playlists`, `navidrome_playlist{id}` (with `hidden`: Coda's `Hidden` as `{kind: none|some{count}|suspect}`, and `truncated`), `navidrome_random_songs` (Navidrome "Shuffle all": the UI plays them with `playTracks`), `navidrome_genres` (`getGenres`; a genre's `id` is `Genre::query`, the server's exact value, and `name` the cleaned one; a value `check_genre` would refuse, over 1,024 chars, is left out so every listed id opens), `navidrome_genre_albums{genre, offset}` (`albums_by_genre`, in the server's order, paged like `navidrome_albums`), `navidrome_genre_random_songs{genre}` (`random_songs_in_genre`, 500; the genre page's Shuffle), `navidrome_search{query}` (`search3`, 20/20/50). A genre value from the UI is non-empty and at most 1,024 chars (`check_genre`), sent untrimmed and never logged.
  - Covers for albums, artists and playlists go through the same registry (`CoverService::url_for_key`): local = the first track's art, Navidrome = the item's `coverArt`.
- **Local ids**: `"<generation>:<n>"` for tracks, artists, albums and playlists (indices into the library, valid while it only grows). An id from another generation is `stale` (commands) or skipped with the notice "The library changed; N tracks skipped. Reload the view" (intents); a malformed or out-of-range id is `notFound` / "not in the library". Folders are named by their path of folder names from the root.
- **Queue keys**: `QueueEntryId`'s `Display` (`q12`): stable for the entry's life in this run (React key, intent target), not across restarts.
- **`TrackDto`** also carries `albumId` / `artistId` (local ids, or Navidrome's) for "Go to album/artist"; `null` when unknown. Queue DTOs resolve a local track's id by path when the queue is sent, so a track restored before the scan found it has `id: null` until the queue changes.
- **`TrackRef`**: the shape of a `TrackDto` minus `coverUrl` (`{ source, title?, artist?, … durationMs?, albumId?, artistId?, genres? }`, extra fields ignored), so the UI hands back the tracks a browse call gave it. `source` is `{kind:"local", id}` or `{kind:"navidrome", songId, coverArt}`. Local refs are looked up in the scanned `Library` by id and generation, so non-UTF-8 paths play (metadata comes from the scan; unknown or stale ids are skipped with a notice). Navidrome refs are rebuilt with `Track::navidrome` from the given metadata (cleaned and capped like server data, genres too: `Track::navidrome` cleans, dedupes and caps them at `MAX_GENRES`; `albumId`/`artistId` kept, bounded). `TrackDto.genres` carries every track's genres in tag order, since the backend keeps no browse cache.
- Preferences commands (each rejects with a message to show): `prefs_get()` → `Prefs {accent, accentColor, accentText, accentContrast, swatches, source, lyricsIndex, libraryView}` (`prefs_set_library_view{view}`: `"covers"` or `"list"`, answers with the new state) (`accent` as saved, `"music"`, `"house"` or `#rrggbb`; `accentColor` its colour, the house accent's for `"music"`; `accentText` `#000000` or `#ffffff`, whichever reads better on it; `accentContrast` its WCAG ratio against the base, two decimals; `swatches` = `{name, value, color}[]`); `prefs_set_accent{accent}` (`"music"`, `"house"` or `#rrggbb`, any case, `#` optional; the house amber typed as hex is saved as `"house"`; anything else is refused) → `Prefs` (saved first). `ui_source_get()` → `"local" | "navidrome" | null`, `ui_source_set{source}` (saved at once, the file's other keys kept). 1.x's appearance and theme commands are gone (ADR 0009).
- Notices: `{id, text}`; the backend drops them after 5 s (max 4), `dismissNotice` drops one early.

## Covers
- DTOs carry `coverUrl` = `coda://localhost/cover/<16 hex>` (`http://coda.localhost/...` on Windows/Android); the UI appends `/small` (256 px) or `/large` (1024 px).
- The token is a per-run keyed hash of the `CoverKey`; the registry (≤25,000 tokens, least recently used dropped: a token handed out again moves to the back, so the playing track, the queue and lists on screen keep their covers while a long list is built) is filled when DTOs are built, so the webview can only fetch covers of tracks it was shown and never names a path. Unknown tokens → 404.
- Local: embedded art, else a folder image. Navidrome: `getCoverArt` via the current client, cached in Coda's disk cache (shared with the TUI). Served as JPEG with `Cache-Control: private, max-age=86400`. `[ui] cover_art = false` turns URLs off.

## Lifecycle
- `frame.rs` remembers the window's position, size and maximised state (below); `tauri-plugin-window-state` was replaced by it.
- Window close / last window closed / media-controls Quit → `RunEvent::ExitRequested`: prevent the exit, `begin_quit` (wait ≤3 s for a running settings save (`SettingsLock`), run `EngineHandle::shutdown`, then `app.exit(0)`).
- SIGTERM, SIGINT and SIGHUP (`watch_signals` in `lib.rs`) take the same `begin_quit` path (so they also wait for a settings save); a second signal while quitting terminates mpv and exits at once.
- `RunEvent::Exit` without a finished shutdown (a quit path that skipped `ExitRequested`, such as macOS Cmd+Q or the Dock's Quit: `terminate:` reaches tao only as `applicationWillTerminate`, so Tauri sends `Exit` alone): blocking, bounded (8 s) shutdown on the event-loop thread.
- A startup still running at exit gets 3 s, then is aborted *and awaited*, which drops a finished-but-unclaimed `PlaybackHandle` before the reply.
- `coda-core`: dropping a `PlaybackHandle` without `shutdown` while its backend runs sends mpv SIGTERM synchronously; on Linux mpv is spawned with `PR_SET_PDEATHSIG = SIGTERM` (covers SIGKILL and aborts); mpv is also spawned with `kill_on_drop`.
- Panics: the app records mpv's pid (`bootstrap::MPV_PID`); a panic hook terminates it when the panic ends the process (always under the `release-gui` profile's `panic = "abort"`, or on the main thread).
- Session saves that fail are retried with back-off (2 s doubling to 60 s), not only at exit.

## Security

- Window state and full screen (`src-tauri/src/frame.rs`): every launch is windowed. Frames are in logical units (points: the same on every screen; physical pixels depend on each screen's scale), converted with the window's scale at the same event. `frame::Tracker` follows `Moved`/`Resized` while the window is windowed (not minimised); a maximised state keeps the frame from before and only sets `maximized`, and a full-screen one is never recorded. Both fall back to the *settled* frame, the last one that stayed unchanged for at least 500 ms (promoted when the next change arrives), because the resizes leading to them are not the window's own (GTK may report the screen-sized configures before the state; a macOS zoom animates through intermediate sizes); on Linux the GTK watcher reports full screen too. `frame::save` writes the last windowed frame (`{version: 1, x, y, width, height, maximized}`, atomically, skipped when unchanged since the last write or the restore) to `<state>/coda-app/window.json` on `CloseRequested`, `ExitRequested` and `RunEvent::Exit` (macOS Cmd+Q and the Dock's Quit arrive only as `Exit`, see Lifecycle). `frame::saved` reads it before the window is built: the builder gets its `inner_size`, and its `position` when a screen (each converted with its own scale) still shows at least 100×100 points of it, so the window first shows in place without a jump; a saved maximised state is applied right after `build()`. A missing, malformed, versionless (the earlier physical-pixel file) or out-of-range file (sizes 200–20,000, positions within ±100,000) leaves the configured default. `tauri-plugin-window-state` was dropped: it saved the full-screen frame as the window size and restored a maximised window at a position only its own move tracking kept. Full-screen state: Tauri's `is_fullscreen` is the value the app last set (on Linux a window manager's full screen is invisible to it, LESSONS), so `frame::is_fullscreen` reads GDK's window state on Linux (main thread) and Tauri's elsewhere; the `window_is_fullscreen` command returns it, and on Linux a GTK `window-state-event` handler emits `window-fullscreen` (bool) when it changes (the resize that goes with it may arrive before GTK's state changes).

## Platform, packaging, CI
- Linux is built and tested in Docker: `docker/linux-dev.Dockerfile` (Debian trixie, native arch; Rust stable, Node 22 + pnpm 12.8.1, the webkit2gtk-4.1/GTK dev packages, mpv, PulseAudio) and `scripts/linux-check.sh` (pnpm build, fmt, clippy, tests, ignored mpv tests against a PulseAudio null sink, `tauri build --debug --no-bundle`; `--bundle` adds deb/AppImage/rpm; `--shell`). Linux target dir, cargo registry, pnpm store and `node_modules` are named volumes, never the host's.
- The engine's MSRV (`coda-core` `rust-version = 1.89`) makes Cargo's resolver hold `tauri` at 2.11.x (2.12 needs 1.90), so `@tauri-apps/api` is pinned to `~2.11` to match (`tauri build` refuses mismatched minors). Raise both together.
- `tauri.conf.json` `bundle`: targets deb, appimage, rpm (Linux) and app, dmg (macOS); category Music; deb/rpm depend on `mpv`; macOS 11+. Icons are generated from `src-tauri/icons/source/icon.svg` (the coda sign in the accent amber).
- `packaging/arch/PKGBUILD` (package `coda-app`) builds a committed ref of a local checkout with `tauri build --no-bundle` and installs the binary, `packaging/linux/coda-app.desktop`, hicolor icons and the license.
- `.github/workflows/coda-gui-ci.yml` (repository root, `working-directory: apps/coda-gui`): rustfmt; per OS (ubuntu-latest, macos-latest) pnpm build, clippy and tests of `coda-app` and `coda-core`, `tauri build --debug --no-bundle`, plus the ignored mpv tests on Linux. `coda-gui-release.yml` (tags `coda-gui-v*.*.*`): checks the tag against tauri.conf.json, Cargo.toml and package.json, builds bundles with `--profile release-gui` on ubuntu-24.04 (x86_64, arm64) and macos-latest (arm64), creates a draft release (`--latest=false`) with checksums. Actions are pinned by SHA; permissions are read-only except the publish job.
